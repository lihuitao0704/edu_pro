目录 联动与架构 总体汇报
代码核验版 · 金融级记忆闭环

记忆不是“把聊天记录塞进 Prompt”，
而是受权限、时效与事实约束的决策上下文

本页以当前仓库实现为基线，区分会话上下文、客户画像、业务事实、语义知识、关系图谱和审计证据；所有 Agent 只读取被授权的最小必要上下文，业务事实始终以 MySQL 为准。

严格结论

原图方向正确，但不能直接作为最终记忆架构

它识别了 Redis、MySQL、Milvus、Neo4j 与 Memory Manager，但混入了通用应用链路，未写清数据权威性、键级隔离、TTL、失效、事件幂等和知识源追溯；这些恰恰是金融系统记忆是否可信的关键。

纠正

事件总线应按代码标注

当前实现为 MySQL 事务 Outbox + Redis Pub/Sub，不是 Redis Streams / Kafka：提交成功后才广播，消费通过 agent_event_consumption 去重。图中不应把未落地的消息中间件写成既有能力。

核心原则

“快”与“准”各有归属

Redis 提供短时状态与缓存；MySQL 保存业务事实和审计；Milvus 只做语义召回；Neo4j 做关系投影；MinIO 保存原始知识文件。任一缓存或模型输出都不能替代合规事实源。

需求映射：需求文档要求“短期 Redis、中期 MySQL + Redis、长期 Milvus + Neo4j + MinIO”，并以 RAG / GraphRAG 支撑问答与推荐。本架构进一步补齐了业务事实、会话归档、事件一致性和金融合规治理的边界。

一次请求如何安全读取“记忆”

读路径 / 当前实现

按可信度和时效组装，不把所有库灌入 Prompt

  1. 身份定界。认证结果绑定 actor_id、role、目标 customer_id；Memory Manager 以会话拥有者隔离上下文。
  2. 会话优先。读取 Redis 消息与路由上下文；Redis 失效时，消息可降级从 conversation_archive 恢复。
  3. 事实优先。画像服务先读 profile:{customer_id}，未命中回源 MySQL；敏感办理再读取正式风险状态与规则。
  4. 按意图检索知识。FAQ、产品、政策分别路由至 Milvus 集合，RAG 经过 rerank 与阈值过滤，并带回 source_info。
  5. 补充关系证据。投顾场景读取 Neo4j 的客户—持仓—产品关系；图谱不可用时不替代 MySQL 的业务判断。
  6. 受控注入。LLM 只获得经裁剪的会话、画像摘要、检索证据与规则结果；最终输出仍要经过安全过滤和审计。
读路径 / 必须坚持的边界

金融事实不能被“记忆召回”覆盖

  • 交易、余额、持仓、正式风险等级：必须从 MySQL / 规则引擎实时读取，绝不能信任历史 Prompt、缓存或向量片段。
  • 知识引用：Milvus 命中只代表相关性；需关联 fin_knowledge_meta 的状态、版本、过期时间和原文件来源。
  • 多角色隔离：顾问代客服务必须记录 actor 与 customer 两个主体；同一 session_id 不能跨主体复用。
  • 降级：Redis、Milvus、Neo4j 不可用时可以降级，但交易风控不可绕过正式规则、适当性与二次确认。
  • 上下文预算：现有消息截断约 4,096 Token；建议为画像摘要、RAG 片段、图谱摘要分别设预算和优先级。
架构判断：Memory Retrieval 是“取证和压缩”的服务，不是“授权和裁决”的服务。授权由认证/RBAC 决定，裁决由规则、适当性和业务服务决定。

一次业务变化如何更新“记忆”

业务操作 / 风评完成交易、持仓、画像、预警、推荐反馈
→
MySQL 同事务写入业务事实 + agent_event_outbox
→
Outbox Relay提交后轮询，失败保留重试
→
Redis Pub/Sub领域事件实时广播
→
幂等消费者event_id + consumer 防重
→
失效 / 投影 / 提醒profile cache、风险上下文、Neo4j、客服提示

这条链路解释了“事实先落库、再通知”的原因：Redis 广播是实时协作层，不是可靠事实源；事件重复投递不会重复修改画像或重复触发下游处理。

更新实例

交易成功后的记忆更新顺序

  1. 交易服务提交 fin_transaction、持仓等业务数据；相关适当性、确认和操作记录留痕。
  2. Outbox写入 transaction_completed 等领域事件，避免“库已提交但通知丢失”。
  3. 消费者失效 profile:{customer_id}，使下一次画像读取回源最新事实；必要时刷新风险投影。
  4. 图谱同步把变化投影到 Neo4j；若失败，重试表与定时任务保证可观察、可补偿。
  5. 后续会话投顾、客服或风控再按权限读取新状态，形成 Agent → Event → Memory → Agent 的闭环。
禁止路径

以下做法会破坏金融级一致性

  • Agent 直接把“用户说已购买”当作交易事实写进画像或 Neo4j。
  • 仅向 Redis 发布事件，却没有数据库 Outbox 和失败恢复记录。
  • 将情绪、市场新闻或模型推断直接上调 / 下调正式 C1–C5 风险等级。
  • 把原文件、元数据、向量检索结果拆开管理，导致答案无法追溯来源版本。
  • 缓存失效后仍把缓存当成权威数据，或将顾问对话上下文泄露给其他客户。

最终架构结论：项目已经具备多层记忆和事件闭环的核心骨架。要达到金融级可上线标准，重点不是再增加一个“记忆库”，而是将每类数据的权威来源、访问主体、存活时间、失效条件、证据来源、可删除性和降级策略写成可执行的制度与代码。
