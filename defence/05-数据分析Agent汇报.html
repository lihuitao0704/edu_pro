答辩主题 · 我负责的数据分析与总体框架优化

把“人找数据”变成受控的自然语言分析，
再把可信洞察接入金融级协同闭环

我负责数据分析 Agent 的整体链路与总体框架优化：让业务人员用自然语言查询客户、产品、持仓和交易数据；让模型只生成候选 SQL；让规则、权限和证据决定查询能否执行；再把有来源、有阈值、可复核的洞察以事件方式提供给画像、风控和投顾。

核心结论：我让员工能够进行受控的自然语言分析，同时把 SQL 执行权牢牢留在规则层。只有通过五道安全闸门且满足洞察白名单的结果，才能成为其他 Agent 的受控输入。
需求映射：需求文档 Phase 2 的 F2.3 要求 NL2SQL 支持业务人员自然语言查询、动态 Schema、Few-shot、只读 SQL 校验和结果解释；Phase 5 要求分析结果支持其他 Agent 决策。当前项目将其落为 NL2SQLService、/api/chat/analyst、洞察白名单、事务 Outbox 与 Redis 事件订阅链路。

本人负责范围

01

数据分析 Agent 全流程

负责自然语言问题到安全 SQL、查询结果、图表/解释和结构化洞察的完整链路。重点不是“让大模型会写 SQL”，而是让它在金融数据边界内可审计地工作。

  • 问题理解、领域 Schema 选择与 Few-shot 提示
  • 只读 SQL 校验、行数限制、敏感字段与异常兜底
  • 分析仪表盘指标与可解释结果输出
02

总体框架优化

将“同步 Agent 调用”优化为“同步服务结果 + 异步领域事件”。聊天响应不等待所有后续动作，关键状态通过 Outbox 可靠落库后再广播，避免业务结果与事件通知不一致。

  • Router + Chat Orchestrator 的统一入口
  • Outbox 可靠发布、Redis Pub/Sub 实时订阅
  • 画像缓存失效、风险联动、审计与 Trace 追踪

数据分析整体流程：模型负责理解，系统负责约束

代码入口：app/api/chat.py 的分析接口调用 app/service/nl2sql_service.py。返回的不只是结果表，还包括实际 SQL 与解释，方便业务复核与答辩演示。

输入

员工以自然语言提出分析问题。系统先经过登录、RBAC、会话归属和输入安全过滤，避免把“可问”误解为“可查全部数据”。

输出

输出由查询结果、图表适配数据、解释口径、实际 SQL 和洞察证据组成。模型不能直接给风险评级或执行操作，只能形成可被后续 Agent 消费的受控信息。

NL2SQL 的五道安全闸门

闸门 1

意图与权限前置

Router 仅将分析类需求送往 NL2SQL；结合登录身份、角色和客户范围，避免把客服问答或交易命令误送为数据查询。

闸门 2

动态 Schema 注入

仅注入问题相关的业务表、字段说明和示例。需求文档要求的 10 张核心业务表与注释用于缩小模型选择空间，而不是暴露全库结构。

闸门 3

只读 SQL 白名单

SQL 必须以 SELECT 开头；INSERT、UPDATE、DELETE、DROP、DDL 和多语句均被拦截。模型只负责生成草案，规则层决定能否执行。

闸门 4

业务边界与结果限制

限制可访问表范围、过滤危险关键字，查询结果最多 100 行。这样既防止越权/误操作，也避免一次查询形成不可控的大量数据暴露。

闸门 5

解释、审计与异常兜底

返回 SQL 与业务解释，异常查询有明确失败结果；Trace、会话归档与审计记录能够还原“谁在何时问了什么、系统查了什么”。

答辩要点

可用不等于可执行

这套设计将自然语言的便利限制在“受控查询”内。数据分析 Agent 可以提供证据，但不能绕过合规、风控和业务审批去改变账户状态。

亮点：分析洞察不是“看到了就广播”

分析洞察白名单

app/service/insight_extractor.py 只抽取有限、可解释的结构化信号。例如：组合回撤 pnl_drawdown ≤ -10%，或周交易次数 weekly_count ≥ 10。每条洞察需要客户标识、时间、数值与来源证据。

这解决了“LLM 生成一句看似合理的结论，就触发金融动作”的风险：没有证据、字段不完整或不在白名单的结果，最多作为页面解释，不会成为事件。

洞察的事件驱动闭环

分析结果满足白名单后形成 analytics_insight 事件，先写入业务事务与 agent_event_outbox，由 Outbox Relay 可靠发布；Redis Pub/Sub 再将事件推送给画像、风控等订阅者。

画像 Agent 可更新偏好或行为标签，RiskMonitor 可生成待核验风险线索；任何正式风险评级与交易处置仍需各自规则和审批链路确认。

总体框架优化：从需求蓝图到当前工程实现

统一编排，而非 Agent 直连

需求文档提出多 Agent 协同；当前工程以 Chat Orchestrator 统一管理会话、上下文与响应，以 RouterAgent 做意图分流。这样客服、投顾、风险、操作、分析的入口规则保持一致。

可靠事件，而非“调用成功即认为通知成功”

需求中的 Redis 事件总线在当前实现中补强为“事务 Outbox → Outbox Relay → Redis Pub/Sub”。当消息发布暂时失败时可重试，降低业务写入成功但订阅方完全不知情的概率。

分层记忆，而非单一聊天记录

Redis 保存短期会话与画像缓存；MySQL 保存交易、事件和审计事实；Milvus 承载 RAG 语义检索；Neo4j 保存客户—产品—持仓关系。不同记忆服务于不同决策时效与可追溯性。

可观测与降级

TraceService 记录链路与 Agent span；RAG、图谱和模型不可用时支持明确的降级策略。对金融场景而言，系统应当“可解释地少做”，而不是在不确定状态下自动多做。

现场演示建议（3 分钟）

第一步

问一个业务问题

以“近三个月高净值客户偏好哪些产品？”展示自然语言入口、分析路由与结果页。

第二步

解释安全边界

展示生成 SQL、只读限制、100 行限制；补充一个写操作示例，说明它会在规则层被拒绝。

第三步

讲清协同价值

以异常交易频率或回撤为例，说明有证据的洞察如何经 Outbox 进入画像/风控，而不是直接改变客户账户。

答辩结论：数据分析 Agent 的创新点不只是 NL2SQL，而是将“自然语言理解—受控读取—可解释洞察—可靠事件—多 Agent 消费”串成了一条可治理链路；总体框架的价值则在于把每个智能能力放进权限、审计、记忆和风控边界之内。
