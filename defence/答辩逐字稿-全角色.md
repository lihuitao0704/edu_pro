# 智能财富管家系统 — 答辩逐字稿

> 建议时长：约 15-20 分钟。适合毕业答辩或项目评审场合。
> 本文档按角色视角（智能客服、投顾、理财经理、风控、数据分析）组织，
> 每个角色讲解 Agent 功能、业务流转、输入→处理→输出。

---

## 一、开场（约 1 分钟）

各位评委老师，大家好。

我今天汇报的项目是「智能财富管家系统」——一个基于 Multi-Agent 协作架构的 AI
驱动财富管理平台。

这个项目的核心命题是：**如何让多个 AI Agent 在金融业务的严格合规约束下，
各司其职又能联动协作，真正为不同角色（客户、投顾、理财经理、风控专员、管理
层）提供智能化服务。**

我的答案是：**用 Router Agent 做统一调度，用领域事件总线做异步联动，用
"Outbox + 幂等消费账本"保证消息不丢不重，用五道安全闸门守住数据安全边界。**

整个系统包含六大业务 Agent：

| Agent | 职责 | 核心技术 |
|-------|------|---------|
| 智能客服 Agent | RAG检索 + LLM生成 + C4风控联动 | Milvus向量检索 + Redis风险上下文 |
| 投顾 Agent | 画像分析 + 产品推荐 + 资产配置 | LangChain Agent + 7工具LLM自主编排 |
| 业务操作 Agent | 申购/赎回/转账等实操 | NL2API + P0-P5全量合规校验 |
| 风控 Agent | AML规则预警 + C1/C2/C4联动 | 规则引擎 + 事件总线广播 |
| 数据分析 Agent | NL2SQL + BI仪表盘 | 五道安全闸门 + 分析洞察白名单 |
| 客户账户 Agent | 客户本人查询持仓/交易/画像 | 身份强绑定 + 隐私保护 |

## 二、从智能客服角度答辩（约 3 分钟）

### 2.1 Agent 功能定位

智能客服 Agent 是客户接触系统的第一入口。它的核心职责是：
- 回答客户关于金融产品、业务流程、政策规则的各类问题
- 在客户提到敏感操作时，自动联动风控系统展示风险提示
- 当 AI 回答不了时，平滑转接人工客服

### 2.2 业务流程（输入→处理→输出）

**输入**：客户在前端聊天框输入自然语言问题，比如"最近有什么低风险产品？"

**处理流程**：

第一步 — **输入安全过滤**：
客服 Agent 启动时首先调用 InputSafetyFilter，对客户的消息做恶意内容检测。
如果命中拦截规则，直接返回安全提示，消息不会送到 LLM。

第二步 — **意图识别**：
客服 Agent 调用 IntentService 对客户问题做子意图分类。可能的结果有：
- `faq` — 产品/业务 FAQ 类问题
- `product_inquiry` — 产品咨询
- `policy_interpretation` — 政策解读
- `transfer_human` — 要求转人工
- `chitchat` — 闲聊

意图分类的置信度如果达到 0.95 以上，会跳过一些冗余检查，加速响应。

第三步 — **跨 Session 记忆召回**：
客服 Agent 调用 MemoryRecallService，从历史对话归档中召回三类信息：
- 客户画像摘要（风险等级、持仓概览）
- 历史偏好（之前喜欢问什么类型的问题）
- 近期对话记录（上次聊了什么、有没有未解决的问题）

这些信息注入到 LLM 的上下文中，让 AI 客服能"记住"这个客户。

第四步 — **RAG 检索（检索增强生成）**：
RAGService 把客户问题转成向量（通过 Ollama Embedding），去 Milvus 向量数据
库中做语义搜索。返回 Top K 个最相关的知识片段，然后通过 RerankerTool 做重排
序，把最精准的片段排在最前面。

如果 RAG 检索的置信度不够高，系统会走关键词兜底匹配——用预定义的金融领域高
频问题模板做回答。
如果连兜底都不匹配，系统会诚实地说"这个问题需要人工客服来回答"。

第五步 — **C4 风控联动**：
这是客服 Agent 的一个重要设计。当客户的消息中包含敏感操作关键词（大额转账、
大额赎回、大额申购等），系统自动触发 C4 联动：
- 从 Redis 读取 `cs_risk_ctx:{customer_id}` 缓存（由风控 Agent 实时维护）
- 查询 MySQL 中客户的 `risk_flag`（normal/warning/high）
- 统计近30天的未处理风控预警数量
- 根据风险等级在回复前自动附加风控提示

具体提示模板：
- `high` 级别："⚠️ 您的账户当前处于高风险关注状态。大额交易可能触发风控审
  核，建议联系您的理财顾问确认交易细节。"
- `medium` 级别："ℹ️ 您的账户近期有交易活动触发风控关注。如涉及大额交易，
  系统可能会要求二次确认。"
- `low` 级别："✅ 您的账户风险状态正常，可正常办理业务。"

第六步 — **LLM 增强生成**：
把所有信息（知识片段 + 对话历史 + 客户画像 + 历史偏好 + 客户问题）组装成
Prompt，送给 LLM。LLM 按要求输出 JSON 格式：
```json
{
  "reply": "回答内容",
  "sources": ["来源1", "来源2"],
  "need_human": false,
  "confidence": 0.85
}
```

第七步 — **安全审核与合规检查**：
- 内容安全审核：SafetyService 检查 LLM 生成的内容是否合规
- 金融风险提示：如果回答涉及产品或收益，自动在末尾附加风险声明
- 审核不通过 → 替换为兜底回复

第八步 — **记忆归档**：
把本轮对话写入 Redis 短期记忆 + MySQL 长期归档，下次对话时可以召回。

**输出**：一段包含知识解答、来源引用、风控提示（如有）、风险声明（按需）的
完整回复。

### 2.3 亮点总结

- **RAG + 记忆召回**：AI 客服不只是"搜索然后回答"，而是结合客户画像和历史
  对话做个性化回复
- **C4 风控联动**：客服和风控不是孤立的系统，客服Agent实时感知客户风险状态
- **多层兜底**：RAG不足→关键词匹配→转人工，保证服务不中断
- **合规内置**：金融风险提示不是事后加的，而是流程中内置的强制环节

## 三、从投顾角度答辩（约 4 分钟）

### 3.1 Agent 功能定位

投顾 Agent 是整个系统最核心的 Agent，它服务于理财顾问和客户两个角色。它的设
计理念是「LLM 自主决策 + 多工具编排」，而不是传统的 if/elif 规则路由。

投顾 Agent 拥有七个工具：

| 工具 | 功能 |
|------|------|
| smart_recommend | 一键智能推荐（画像+预警+推荐+配置） |
| profile_tool | 查客户风险画像（四维度+熔断） |
| recommend_products | 产品推荐打分排序 |
| asset_allocation | 资产配置比例建议 |
| analysis_holdings | 持仓分析（MySQL+Neo4j） |
| compare_customers | 两个客户对比分析 |
| graphrag_search | 知识图谱+向量文档检索 |

### 3.2 业务流程（输入→处理→输出）

**输入**：理财顾问说"给客户张三推荐3款产品，他预算10万，比较保守"

**处理流程**：

第一步 — **意图路由**：
Router Agent 识别为 `investment_recommendation` 意图，置信度 0.95，分发到
投顾 Agent。

第二步 — **客户身份校验**：
AdvisorAgent 先调用 `_validate_customer_id` 做三道校验：
- ID 格式是否合法？
- 该 ID 对应的用户类型是否为 CUSTOMER（不是员工账号）？
- 客户状态是否正常（非冻结/注销）？

如果校验失败，直接返回错误提示，不会进入 LLM 环节。

第三步 — **投顾子意图分类**：
系统对理财顾问的消息做二次意图分类：
- `product_recommend` → 产品推荐意图
- `portfolio_analysis` → 持仓分析意图
- `asset_allocation` → 资产配置意图
- `comparison` → 客户对比意图

如果置信度 ≥ 0.80，系统会给 LLM 加一个轻量级的"意图提示"，帮助 LLM 更快选
择正确的工具。比如："（意图提示：用户意图为「产品推荐」，优先调用
smart_recommend 工具）"

第四步 — **跨 Session 记忆召回**：
MemoryRecallService 召回该客户的历史偏好和画像摘要。如果之前投顾给该客户推
荐过某类产品但被拒绝，LLM 会在推荐时自动避开。

第五步 — **LLM 决策 + 工具调用**：
这是投顾 Agent 最核心的环节。LLM 根据 System Prompt 中的工具调用策略，自己
决定：
- 调用哪个工具？（本例中选 smart_recommend）
- 按什么顺序调用？
- 拿到工具返回后如何组合？

这里的关键设计是 **smart_recommend（一键智能推荐）**，它把画像查询、风控预
警检查、产品推荐、资产配置四步封装在一个工具调用中。LLM 看到"推荐产品"的
问题，直接调 smart_recommend，一次工具调用完成全部工作，避免了多轮工具调用
的延迟叠加。

smart_recommend 内部做了什么：
1. 查风控预警：近30天 pending 状态的预警。high → 限制 R1-R2，medium → 限制
   R1-R3
2. 查风评有效期：缺失/过期 → 降级到 C1 处理，提示客户重新测评；如果没有画
   像但数据库有基础数据 → 自动调用 ProfileService.assess() 修复画像
3. 查客户画像：四维度得分 + 熔断规则 + 风险等级
4. 综合限制条件：熔断限制 + 风控预警限制 → 确定最终产品范围
5. 推荐产品：在允许范围内按匹配度打分排序
6. 资产配置建议：根据客户实际风险等级（被限制后的等级）给出配比
7. 返回结构化 JSON

第六步 — **LLM 生成回复**：
LLM 拿到 smart_recommend 的结构化 JSON 后，按照 System Prompt 中的输出规范
生成 Markdown 格式的回答：

```
> 当前客户推荐正常完成  ← 状态提示（有异常时才出现）

## 风控预警  ← 有预警时才出现
（高风险/中风险预警信息）

## 客户风险画像
- 风险等级：C3 平衡型
- 综合评分：75/100

## 产品推荐
| 产品名称 | 风险等级 | 预期收益 | 匹配度 | 推荐理由 |
|---------|---------|---------|-------|---------|
| ...     | ...     | ...     | ...   | ...     |

## 资产配置建议
货币类 15% | 债券类 50% | 混合类 25% | 现金 10%

> ⚠️ 风险提示：投资有风险，入市需谨慎...
```

第七步 — **投资金额配置计划**：
如果理财顾问的消息中包含了投资金额（如"10万"），系统会：
- 从消息中用正则提取金额："10万" → 100000
- BudgetAllocationService 根据推荐产品列表和资产配置，计算每只产品建议投入
  多少钱
- AdvisorNarrativeService 生成带金额配置的完整回复

第八步 — **角色差异化的回复策略**：
- 面向理财顾问：LLM 原文输出，保留专业的 Markdown 格式，展示完整的分析过程
- 面向客户本人：走 AdvisorNarrativeService.render_customer() 模板，把理财顾
  问的专业术语转成客户易懂的语言，隐藏内部技术细节

第九步 — **流式输出（SSE 真流式）**：
投顾 Agent 支持 token 级的 SSE 流式输出。对于理财顾问，系统实时推送 LLM 的
每个输出 token，理财顾问能看到 AI "一边思考一边写"。同时，工具调用完成的时
间点也会通过 `event: tool_end` 推送到前端，让投顾知道分析进行到哪个阶段了。

对于客户角色，系统采用"先跑完 Agent → 再用模板生成回复 → 逐字流式输出"的
策略。客户看到的是流畅的"打字机效果"，而不是 LLM 可能有的停顿和跳变。

第十步 — **记忆归档**：
保存本轮对话到 Redis 短期记忆 + MySQL 长期归档。

**输出**：一份包含画像解读、产品推荐、配置建议、投资金额计划、风险提示的
完整投顾报告。

### 3.3 亮点总结

- **LLM 自主编排而非规则路由**：投顾 Agent 不是预定义的 if/elif 流程，LLM
  根据自然语言理解，自主决定调用哪些工具、按什么顺序调用
- **smart_recommend 一键推荐**：把四步操作合并为一次工具调用，显著降低延迟
- **多层次风险校验**：手动校验 + LLM 自主 + 风控预警 + 熔断规则 + 适当性匹
  配，五层防护
- **角色差异化回复**：同一份分析结果，理财顾问看到的是专业报告，客户看到的
  是通俗解读
- **流式体验**：理财顾问能看到 AI 实时思考过程，客户能看到流畅的逐字输出

## 四、从理财经理（业务操作）角度答辩（约 3 分钟）

### 4.1 Agent 功能定位

业务操作 Agent 采用了 **NL2API** 架构：自然语言 → LLM Function Calling →
意图识别 + 参数提取 → 权限校验 → 合规校验 → 执行操作。

理财经理可以执行的 14 种操作涵盖：申购、赎回、转账、风评重做、信息更新、产
品查询、持仓查看、审计日志查询、客户全景视图、可疑交易上报、工单创建等。

### 4.2 业务流程（以申购为例，输入→处理→输出）

**输入**：理财经理说"帮张三申购 10 万元的天天利货币基金"

**处理流程**：

第一步 — **LLM Function Calling**：
系统将 14 个工具的 Function Definition 发给 LLM，LLM 理解用户意图后自动
调用：
```json
{
  "name": "purchase_product",
  "arguments": {
    "customer_name": "张三",
    "product_name": "天天利货币基金",
    "amount": 100000
  }
}
```

第二步 — **权限校验（RBAC）**：
系统检查当前操作员的角色是否在申购权限白名单中。理财顾问和管理员可以执行
申购，客户经理和风控专员不可以。

第三步 — **参数解析与实体识别**：
- "张三" → 通过 graph_query_tool 在 Neo4j/MySQL 中解析为客户 ID
- "天天利货币基金" → 解析为产品 ID
- "100000" → 安全转为浮点数（使用 Decimal 中间层防精度丢失）

第四步 — **P0~P5 全量合规校验**（这是系统最严格的校验链路）：

P0 — 交易时间校验：
- 检查是否周末（周六日 → 警告不阻止）
- 检查是否法定节假日（2026年节假日硬编码 → 警告不阻止）
- 检查是否在交易时间 9:30-15:00（非交易时间 → 警告不阻止）

P1 — 适当性匹配校验：
- 查客户风评等级（如 C3）
- 查产品风险等级（如 R1）
- 计算匹配：C3 可以买 R1-R3 产品
- 如果不匹配但差一级（C2 买 R3）→ 需要签署风险揭示书
- 如果完全不匹配（C1 买 R5）→ 直接拒绝
- 风评缺失 → 拒绝，提示先做风评

P2 — 风评有效期校验：
- 风评有效期一年
- 过期 → 拒绝，提示重新测评

P3 — 产品状态校验：
- 产品是否在售？
- 是否暂停申购？
- 是否已下架/已结清？

P4 — 客户状态校验：
- 账户是否正常？
- 是否被冻结？

P5 — 风控与反洗钱校验：
- 客户是否有高风险标记（risk_flag=high）？
- 近30天是否有待处理风控预警？
- 单日累计限额检查：200万/天
- 起购金额检查
- 申购金额倍数检查：100元的整数倍
- 产品剩余额度检查：募集额度是否够

第五步 — **二次确认机制**：
金额超过 1 万元 → 需要理财经理二次确认。系统把待确认参数存入 Redis（TTL 2
分钟），生成确认摘要，等待理财经理回复"确认"。

涉及资金超 50 万 → 强制要求填写备注原因：
```
"确认 备注：客户主动要求购买理财"
```

涉及风险揭示 → 需要额外的风险揭示确认：
```
"确认风险揭示 备注：客户已阅读并签署风险揭示书"
```

如果有人恶意猜测 session_id 或者尝试跨 session 确认别人的操作 → 系统校验
Redis 中的 user_id 必须匹配，不匹配则拒绝。

第六步 — **执行操作**：
1. 写入 fin_transaction 表（交易流水，含 transaction_no）
2. 更新 fin_holdings 表（持仓新增或份额增加）
3. 更新用户余额
4. 如涉及风险揭示，记录 acknowledged_by 和 acknowledged_at

第七步 — **后置处理链**（自动触发，不需要理财经理等待）：
1. 创建审计工单（biz_work_order，自动记录操作审计信息）
2. 发布业务完成事件（通过 Outbox → Redis → 多个消费者）
3. 同步 Neo4j 知识图谱（客户-产品关系）

第八步 — **记忆归档**：
保存操作记录。

**输出**：
```
✅ 申购成功！
• 交易流水号: TXN20260727001
• 产品: 天天利货币基金
• 金额: 100,000 元
• 份额: 99,502.49
• 适用净值日期: 2026-07-27
```

### 4.3 其他重要操作的设计亮点

**赎回操作**特有校验：
- 持仓是否充足（不能赎回不持有的产品）
- 赎回后最低保留份额 100 份（除非全部赎回）
- 单日同一产品赎回次数上限 3 次
- 赎回份额精度最多 2 位小数
- 估值兜底机制：current_value 为空时回退用 cost_amount

**转账操作**特有校验：
- 不能自己转自己
- 转出方余额是否充足
- 转入方账户状态（已注销/冻结 → 拒绝）
- 双方风控标记检查

**客户全景视图**：
一站式展示 7 类信息：基本信息（脱敏）、风险信息、持仓汇总、近期交易、风控
预警、关联客户、行业分布。这是理财经理做客户分析的一站式视图。

### 4.4 亮点总结

- **NL2API 架构**：理财经理不需要记住操作菜单，用自然语言就能办理业务
- **P0-P5 全量校验**：6 层 20+ 项业务校验，覆盖适当性、时限、持仓、风控、
  反洗钱、审计
- **二次确认 + Redis 状态管理**：大额操作不失误，恶意 session 猜测被拦截
- **审计全自动**：每次操作自动生成审计工单，无需理财经理额外操作

## 五、从风控角度答辩（约 3 分钟）

### 5.1 Agent 功能定位

风控 Agent（RiskMonitorService）是系统的"安全大脑"。它包含：
- AML 反洗钱规则引擎（多条规则逐条匹配）
- 预警分级系统（low/medium/high）
- C1/C2/C4 三频道联动机制
- 周期校准调度器
- 风控管理页面

### 5.2 业务流程 — 风控预警如何产生和联动

**触发源**：业务操作 Agent 执行了一笔交易（如申购/赎回/转账）

**处理流程**：

第一步 — **事件产生**：
业务操作 Agent 的事务提交成功后 → 在同一个数据库事务中，把事件写入 Outbox
表。这个设计保证了"业务操作成功"和"事件产生"的原子性——要么都成功，要么
都回滚。

第二步 — **事件广播**：
Outbox Relay 后台任务每秒扫描 Outbox 表 → 发现新事件 → 发布到 Redis 的
`event:agent_domain` 频道。

第三步 — **多消费者并行处理**：
事件到达后，四个消费者组同时处理：

消费者组 1（profile-risk-consumer）— 画像风险消费者：
- 查询客户所有 pending 状态的预警
- 计算最高风险级别
- 更新 fin_customer_profile.risk_flag 字段
- 失效 Redis 画像缓存

消费者组 2（advisor-risk-consumer）— 投顾风险消费者：
- 同样的风险级别计算
- 更新 Redis `risk_flag:{customer_id}`（TTL 24小时）
- 下次投顾做 smart_recommend 时读到这个标记 → 自动限制推荐范围

消费者组 3（customer-service-risk-consumer）— 客服风险消费者：
- 更新 Redis `cs_risk_ctx:{customer_id}`
- 维护 `risk:alert:pending` 集合
- 下次客服对话中自动展示风控提示

消费者组 4（risk-monitor-consumer）— 风控监测消费者：
- 接收可疑交易上报事件
- 转化为正式的 risk.alert.created 领域事件
- 进入风控预警生命周期

第四步 — **幂等消费保证**：
每个消费者有一个幂等账本（agent_event_consumption 表）。处理前先写入
`(event_id, consumer)` 记录 → 成功了不管 → 失败了释放锁 → Outbox 重试。
防重复、防丢失。

### 5.3 风控预警生命周期

风控预警有四个状态流转：
1. `pending`（待处理）→ 刚产生的预警
2. `processing`（处理中）→ 风控专员开始处理
3. `resolved`（已解决）→ 确认为真实风险，已采取措施
4. `false_positive`（误报）→ 经核实为误报

每次状态变更 → 发布对应的领域事件 → 各消费者重新评估客户风险状态：
- resolved 或 false_positive → 减少 active_alert_count
- active_alert_count 归零 → 恢复 risk_flag 为 normal → 取消投顾降权
- 客服风险上下文自动清除

### 5.4 C1/C2/C4 联动机制

**C1 联动（投顾降权）**：
风控预警 → 更新画像 risk_flag + Redis → 投顾下一次推荐时自动限制范围。
这是"全自动"的，不需要人工介入。风险消除后自动恢复。

**C2 联动（风控监测日志）**：
所有交易事件记录到风控日志 → 风控管理页实时展示 → 供风控专员监控。

**C4 联动（客服风控提示）**：
风控预警 → 更新 Redis cs_risk_ctx → 客服 Agent 检查敏感关键词 → 在回复中嵌
入风险提示。Router Agent 在路由阶段也做 C4 预检——有预警客户 + 敏感操作，
强制走客服路径。

### 5.5 亮点总结

- **Outbox + 幂等消费**：事件不丢不重，金融系统的基本要求
- **C1/C2/C4 三频道联动**：一个预警产生后，自动影响投顾、风控监控、客服三
  个维度
- **预警全生命周期管理**：从产生到解决，状态透明可追溯
- **自动恢复机制**：预警解决后自动恢复推荐范围，不需要人工"解封"

## 六、从数据分析角度答辩（约 3 分钟）

### 6.1 Agent 功能定位

数据分析 Agent 让业务人员可以用自然语言查询数据库，并通过 BI 仪表盘查看经营
全貌。它包括两个核心子系统：
- NL2SQL 服务：自然语言 → SQL → 执行 → 解读
- BI 仪表盘：6 大指标实时聚合 + ECharts 可视化

### 6.2 NL2SQL 业务流程（输入→处理→输出）

**输入**：风控专员问"统计近30天各等级风险预警数量"

**处理流程**：

第零层 — **快速预检（拒识）**：
CheckQueryIntent 检查输入是否是业务查询意图：
- "你好" → 拒识，引导用户提问
- "帮我写诗" → 拒识
- "最近" → 太短 + 无业务关键词 → 拒识
- "统计近30天风险预警" → 通过

第一层 — **动态 Schema 选择**：
根据用户问题中的关键词匹配相关表：
- "风险预警" → fin_risk_alert
- "等级" → fin_risk_assessment
- 补充表关系信息帮助 LLM 写 JOIN

第二层 — **LLM 生成 SQL**：
组装上下文（DDL + FK + Few-shot 示例）→ 送给 LLM → 生成 SQL。

第三层 — **五道安全闸门（核心亮点）**：

闸门 1 — 意图预检：已通过
闸门 2 — 最小 Schema：只暴露相关表结构，减少 SQL 幻觉
闸门 3 — 只读校验：
  - 剥离所有 SQL 注释（防止 `/* DROP TABLE */` 绕过检测）
  - 必须以 SELECT 开头
  - 禁止 UPDATE/DELETE/INSERT/DROP/ALTER/TRUNCATE
闸门 4 — 危险语法拦截：
  - 禁止 UNION（防止通过 UNION SELECT 绕过表权限）
  - 禁止 INTO/LOAD_FILE/EXEC/EXECUTE
  - 禁止多语句（分号后面不能有第二个语句）
闸门 5 — 敏感数据与资源边界：
  - 禁止查询 password/api_key/token/id_card 等敏感列
  - 执行结果再做二次脱敏（手机号→138****5678）
  - 最多返回 100 行
  - 缓存按 user_id + query_hash 隔离

这里的关键点是：**LLM 只负责理解问题和生成候选 SQL，真正的执行权在规则校验
和数据库权限边界手里。**这是金融数据分析和普通聊天机器人的本质区别。

第四层 — **执行 SQL + 结果解读**：
执行 SQL → LLM 解读结果 → 生成自然语言解释。

第五层 — **Redis 缓存**：
相同问题 10 分钟内直接返回缓存，减少重复 LLM 调用。

**输出**：
```json
{
  "sql": "SELECT alert_level, COUNT(*) ...",
  "query_result": [{"alert_level": "high", "cnt": 3}, ...],
  "explanation": "近30天共产生15条风控预警...",
  "safety": {"select_only": true, "row_limit": true, "no_sensitive": true},
  "timing": {"generate_ms": 450, "execute_ms": 23, "explain_ms": 1200}
}
```

### 6.3 BI 仪表盘

前端 AnalyticsView 页面使用 Vue 3 + ECharts，6 大指标从数据库实时聚合：
- 客户 AUM 分布（高价值客群识别）
- 风险收益对比（产品风险-收益散点图）
- 热销产品排名
- 月度交易趋势（申购/赎回/转账曲线）
- 风险预警分布（按等级/状态统计）
- 产品货架矩阵（R1-R5 × 产品类型热力图）

### 6.4 分析洞察白名单

关键设计：不是所有 NL2SQL 查询结果都能影响其他 Agent！

只允许提取两类有明确数值证据的分析事实：
- 持仓回撤 > 10%
- 单周交易次数 ≥ 10 次

提取后包装为 analytics_insight 领域事件 → Outbox → Redis 广播 → 画像和风控
消费者处理。

明确边界：分析洞察**决不**修改客户正式的 C1-C5 风险等级。正式评级必须走完整
的"风评问卷 → 规则引擎 → 校准 → 审计"流程。

### 6.5 亮点总结

- **五道安全闸门**：从意图预检到执行过滤，层层设防，每道闸门都能独立拦截
- **LLM 与 SQL 执行分离**：LLM 只负责"理解"和"生成候选"，执行权在规则层
- **分析洞察白名单**：只有可验证的、有证据的事实才能联动其他 Agent
- **绝不修改正式评级**：恪守适当性管理的合规边界

## 七、总结（约 1 分钟）

各位评委老师，回到我最开始提出的命题：**如何让多个 AI Agent 在金融业务的
严格合规约束下，各司其职又能联动协作？**

我的答案是六件事：

**第一，统一路由**：Router Agent 作为中央调度器，所有请求走统一入口，做意图
分类、角色校验、隐私保护、参数提取、分发聚合。

**第二，LLM 自主编排**：投顾 Agent 不依赖固定规则路由，LLM 自己决定调用哪
些工具、按什么顺序，七种工具自由组合。

**第三，安全合规内置**：业务操作 Agent 的 P0-P5 全量校验、数据分析 Agent 的
五道闸门、客服 Agent 的金融风险提示——合规不是事后补救，是流程设计的起点。

**第四，事件总线联动**：C1/C2/C4 三频道让风控预警自动影响投顾降权和客服提
示，Outbox + 幂等消费保证事件不丢不重。

**第五，记忆分层架构**：Redis 短期记忆、MySQL 长期归档、画像缓存跨 Agent
共享，让每个 Agent 都"有记忆"。

**第六，全链路可观测**：Trace、健康检查、运行时指标，每次对话走了什么链路
清晰可查。

这个项目的核心价值不是简单地"用了多个 Agent"，而是让每一个 Agent 的能力都
能在金融业务边界内**被复用、被追溯、被约束**。

我的汇报完毕，谢谢各位老师。

## 八、可能追问简答

**Q1：为什么不用单一 Agent，要用 Multi-Agent？**

A：金融业务场景差异太大。客服需要 RAG 检索和 C4 联动，投顾需要 LLM 工具编排
和多层次校验，业务操作需要 Function Calling 和全量合规校验，风控需要规则引
擎和事件广播。单一 Agent 的 Prompt 会膨胀到不可维护。

另外，隔离本身就是安全机制：客户账户 Agent 只能查自己的数据，数据分析 Agent
的 SQL 必须通过五道闸门，风控 Agent 的评级变更必须走完整审计流程。

**Q2：Router Agent 会不会成为单点瓶颈？**

A：Router Agent 不做业务逻辑，只做意图分类 + 分发 + 聚合。它的职责很薄，主
要的计算开销在下游 Agent。而且 Router Agent 本身也可以水平扩展。

**Q3：事件总线的可靠性如何保证？**

A：三层机制：① Outbox 事务写入（事件在业务事务中原子写入）② Relay 定时广
播（每秒扫描，失败持久化到 event_failed_log）③ 幂等消费账本（每个消费者独
立追踪，防重复处理）。

**Q4：LLM 生成 SQL 的安全性怎么保证？**

A：五道闸门。特别强调的是，剥离 SQL 注释是第一道防线（防止 `SELECT 1;
/*comment*/ DROP TABLE users` 这种注释绕过），只读校验是第二道，危险语法拦
截是第三道。而且执行时还会做二次过滤，敏感列的值直接删除。

**Q5：分析洞察为什么不直接修改风险等级？**

A：风险等级（C1-C5）是适当性管理的核心依据，必须基于正式的风评问卷 + 规则
引擎 + 校准流程。分析洞察可能是趋势信号而非确定性结论。我们把它作为投顾约
束（推荐降权）和风控输入（交易频率监测），但不越俎代庖改正式评级。

**Q6：投顾 Agent 的 LLM 怎么保证推荐不违规？**

A：LLM 做出的推荐决策被多层约束：① smart_recommend 内部硬编码了风险等级匹
配矩阵 ② 熔断规则硬拦截 ③ 风控预警自动降权 ④ System Prompt 明确禁止编造
数据和给出买卖指令 ⑤ 输出审核检查违规内容。LLM 是"解释者"和"编排者"，
不是"决策者"——硬约束在工具层。
