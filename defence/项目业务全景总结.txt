1.1 这个系统是干什么的？

简单说，这是一个「AI驱动的智能财富管理平台」。它把传统券商/银行里需要人工操
作的大量业务，用AI Agent实现了自动化和智能化。

整个系统包含六大业务Agent：
  (1) 智能客服Agent   — 回答客户问题、产品FAQ、转人工
  (2) 投顾Agent       — 客户画像分析、产品推荐、资产配置建议、持仓分析
  (3) 业务操作Agent   — 申购、赎回、转账、风评重做、工单创建等实操
  (4) 风控Agent       — 交易监控、规则预警、反洗钱AML
  (5) 数据分析Agent   — 自然语言查询数据库（NL2SQL）+ BI仪表盘
  (6) 客户账户Agent   — 客户本人查询自己的持仓、交易记录、风险等级

这些Agent不是孤立运行的，而是通过一个"路由大脑"（Router Agent）统一调度，
通过事件总线（Event Bus）联动协作。

1.2 系统的"大脑"：Router Agent（路由层）

所有用户请求都必须经过统一入口 POST /api/chat。Router Agent 是整个系统的
中央调度器：

  用户说话 → Router Agent 做意图分类 → 分发给对应的业务Agent → 返回结果

Router Agent 做的事情很简单：只做路由，不解决业务问题。它的工作流程是：
  (1) 理解用户说了什么（意图分类）
  (2) 提取关键参数（比如客户ID、客户姓名）
  (3) 做风控预检（C4联动——如果客户有高风险标记，敏感操作会被拦截）
  (4) 做隐私保护（客户只能查自己的信息，不能查别人的）
  (5) 做角色权限校验（不同角色能用不同Agent）
  (6) 分发给下游业务Agent
  (7) 如果你一句话里包含多个意图，Router Agent会做多任务拆分和并行执行
  (8) 把各Agent的回复聚合起来，统一返回给用户

意图分类支持这些意图：
  - product_faq              → 客服Agent
  - chitchat                 → 客服Agent（闲聊自动转到客服）
  - investment_recommendation → 投顾Agent
  - risk_control             → 风控Agent
  - data_analysis            → 数据分析Agent
  - business_operation       → 业务操作Agent
  - customer_account_query   → 客户账户Agent（客户查自己的信息）
  - customer_risk_explanation → 客户账户Agent（风险等级解读）
  - customer_recommendation_explanation → 客户账户Agent（推荐解读）
  - customer_transaction_guidance       → 客户账户Agent（交易指导）

1.3 Agent之间的通信方式

系统有两种Agent通信方式：

方式一：Router Agent 直接调用（同步）
  这是最常见的通信方式。Router Agent 在分发意图时，直接 import 对应的业务
  Agent，调用它们的 execute() 或 handle() 方法，等待返回结果。
  流程：用户 → Router Agent → 直接调用业务Agent → 返回

方式二：事件总线 Event Bus（异步联动）
  这是Agent之间"不用等"的通信方式。当某个业务操作完成后（比如客户申购了100
  万基金），系统会通过 Redis Pub/Sub 发布事件，其他Agent订阅后自动处理。

  架构是这样的：
    事务Outbox（MySQL保证事件不丢）
    → Outbox Relay（定时读取，广播到Redis）
    → Redis Pub/Sub（消息中间件）
    → 各Agent独立消费者（订阅自己关心的事件）
    → 幂等消费账本（防止重复处理）

  事件频道划分：
    event:risk_alert:c1     → C1频道：投顾降权 — 高风险客户推荐产品被限制
    event:risk_alert:c2     → C2频道：风控监测 — 规则触发后记录日志
    event:risk_alert:c4     → C4频道：客服联动 — 客服Agent展示风控提示
    event:profile_update    → 画像更新 — 缓存失效
    event:work_order_change → 工单变更
    event:graph_sync        → 图谱同步 — 更新Neo4j知识图谱
    event:agent_domain      → 统一领域事件（新版六Agent通用频道）

  具体举个例子：客户申购了100万的高风险基金
    1. 业务操作Agent执行申购 → 事务提交成功
    2. 在同一个数据库事务里，把事件写入outbox表
    3. Outbox Relay每秒扫描outbox → 发现新事件 → 广播到Redis
    4. 各消费者收到事件：
       - C1消费者：更新Redis中该客户的risk_flag → 下次投顾推荐时会降权
       - C2消费者：风控规则引擎重新评估 → 可能生成预警
       - C4消费者：写入Redis客服风险上下文 → 客服Agent下次对话时展示风控提示
       - 画像消费者：失效缓存，下次读取时从数据库拿最新数据
       - 图谱消费者：同步交易关系到Neo4j知识图谱

1.4 系统的数据底座

  MySQL    — 主数据库，14+张业务表（用户、产品、持仓、交易、画像、预警、工单等）
  Redis    — 缓存 + 会话记忆 + Pub/Sub消息 + 确认状态
  Neo4j    — 知识图谱（客户关系、行业分布、产品关联）
  Milvus   — 向量检索（RAG知识库的语义搜索）
  MinIO    — 文档存储（知识库原始PDF/文档文件）

1.5 记忆架构

  短期记忆 — Redis，按session_id存储对话历史，TTL自动过期
  长期记忆 — MySQL conversation_archive表，永久归档
  画像缓存 — Redis profile:{customer_id}，有更新时主动失效
  跨Session记忆 — 客服/投顾Agent会召回客户画像摘要、历史偏好、近期对话

第二章  从客户角度看业务

2.1 客户能做什么？

客户通过前端界面（Vue 3 SPA）使用系统，主要可以做这些事情：

  (1) 跟AI客服聊天 — 问问题、了解产品、咨询业务流程
  (2) 查看自己的风险画像和风险等级（C1-C5）
  (3) 查看自己的持仓（买了哪些产品，盈亏情况）
  (4) 查询交易记录（什么时候买了什么，卖了什么）
  (5) 查余额和可用资金
  (6) 获取产品推荐和资产配置建议
  (7) 做风险评估问卷（16道题，结果决定C1-C5等级）
  (8) 办理业务：申购、赎回、转账（通过内部员工操作）
  (9) 给对话打分和反馈

2.2 客户跟AI客服聊天是怎么跑的？

输入：客户说"最近有什么好的理财产品？"

处理流程：
  第一步：输入安全过滤
    系统先检查客户说的话有没有恶意内容。如果有不当内容，直接拦截不让LLM处理。

  第二步：意图识别
    系统判断客户是想闲聊、问产品、问政策、还是要转人工。
    如果是问产品，归类为product_faq意图。

  第三步：跨Session记忆召回
    系统会去查这个客户之前聊过什么、有什么偏好、风险等级是什么。
    这样AI客服就知道"你上次问过XX，这次又问YY"。

  第四步：RAG检索（检索增强生成）
    从Milvus向量数据库里搜索跟"理财产品"相关的知识文档。
    把最相关的几条知识片段找出来。

  第五步：LLM生成回答
    把检索到的知识 + 对话历史 + 客户画像 + 客户的问题，一起送给LLM。
    LLM生成JSON格式的回答（包含reply、sources、need_human、confidence）。

  第六步：答案审核
    - C4风控联动：如果客户提到了大额转账/大额赎回等敏感操作，先去查客户
      有没有风控预警。如果有高风险标记，在回复前面加上风控提示。
    - 内容安全审核：检查LLM生成的内容是否合规。
    - 金融合规风险提示：如果回答涉及产品或收益，自动在末尾加上
      "投资有风险，入市需谨慎"的风险声明。
    - 置信度检查：如果RAG检索结果置信度太低，走关键词兜底匹配或提示转人工。

  第七步：记忆保存
    把这一轮的对话写入Redis短期记忆和MySQL长期归档。

输出：一段包含产品介绍、风险提示、来源引用的回答。

2.3 客户查自己的风险等级是怎么跑的？

输入：客户说"查看我的风险等级" 或 "我的风险测评结果是什么"

处理流程：
  Router Agent识别为 customer_risk_explanation 意图
  → 分发给CustomerAccountService（客户账户Agent）

  CustomerAccountService做了以下事情：
    1. 用客户ID去查 fin_risk_assessment 表，取最新一条评估记录
    2. 再去查 fin_customer_profile 表，获取更详细的画像信息
       （四维度得分、综合评分、熔断规则等）
    3. 如果风评已过期（有效期一年），系统会提醒客户重新做测评
    4. 把结果格式化输出：
       - 你的风险等级是C3（平衡型），评分75分
       - 你适合R1-R3级别的产品
       - 你的风评有效期到2027年6月
    5. 注意：客户只能查自己的信息。如果客户说"查客户张三的风险等级"，
       系统会拒绝并提示隐私保护。

输出：客户的风险等级、评分、有效期、适合的产品范围。

2.4 客户查自己的持仓是怎么跑的？

输入：客户说"我的持仓情况" 或 "我现在持有哪些产品"

处理流程：
  Router Agent识别为 customer_account_query 意图
  → 分发给CustomerAccountService

  CustomerAccountService做的事：
    1. 从 fin_holdings 表查该客户所有status='持有中'的持仓记录
    2. 关联 fin_product 表获取产品名称、风险等级
    3. 计算总市值、各产品盈亏比例
    4. 如果客户在Neo4j知识图谱中有数据，还可以展示行业分布
    5. 格式化输出：产品名、份额、市值、盈亏金额、盈亏比例

输出：持仓明细列表 + 汇总数据（总市值、总盈亏等）。

2.5 客户获取推荐是怎么跑的？

输入：客户说"推荐几个适合我的产品" 或 "我适合买什么"

处理流程（这是最复杂的流程之一）：
  Router Agent识别为 investment_recommendation 意图
  → 分发给投顾Agent（AdvisorAgent）
  → 客户身份自动绑定（客户角色只能获取自己的推荐）

  投顾Agent内部调用 smart_recommend 一键推荐工具：

    步骤1：查风控预警
      检查客户近30天有没有未处理的风控预警。
      - 有高风险预警 → 推荐范围限制在R1-R2（最保守）
      - 有中风险预警 → 推荐范围限制在R1-R3
      - 无预警 → 正常按风评等级推荐

    步骤2：查客户风险画像
      先查风评是否有效（是否存在、是否过期）
      - 风评不存在 → 自动尝试用数据库已有数据"修复"创建画像
      - 修复失败 → 降级按C1（保守型）推荐
      - 风评已过期 → 降级按C1推荐，提示客户重新测评
      - 风评正常 → 用实际等级推荐

    步骤3：查熔断规则
      如果触发了熔断（比如年龄超大+高风险产品），推荐范围被限制

    步骤4：产品推荐
      根据客户的风险等级和上面的各种限制，匹配适当的产品
      - R1(R2(R3(R4(R5逐级匹配
      - 计算匹配度打分
      - 返回Top N推荐产品

    步骤5：资产配置建议
      根据风险等级给出资产配置比例建议
      - C1保守型：货币60%、现金40%
      - C2稳健型：债券60%、货币30%、现金10%
      - C3平衡型：债券50%、混合25%、货币15%、现金10%

  然后LLM按模板生成回复：
    - 风控预警（如果有）
    - 客户风险画像摘要
    - 产品推荐列表（表格形式）
    - 资产配置建议
    - 投资金额配置计划（如果客户说了"我有10万"）
    注意：回复面向客户时，前端走的是 AdvisorNarrativeService 的"客户友好"模板。
    投顾Agent内部先用理财顾问的专业语气处理，再由模板转换成客户易懂的语言
    "您的风险等级是平衡型，以下是适合您的稳健产品..."

  流式输出（SSE）：
    对于客户角色，系统采用特殊处理：
    - Agent先跑完所有工具调用（查画像+推荐+配置）
    - 然后由 AdvisorNarrativeService 生成客户友好的模板回复
    - 逐字推送给前端（客户看到的是AI在"实时打字"的效果）
    - 理财顾问角色才看到LLM的原始逐token输出

输出：一段包含风险解读、产品推荐、配置建议、风险提示的完整回复。

3.1 投顾能做什么？

投顾Agent是理财顾问的核心工具，它提供七大能力：

  ① 一键智能推荐（smart_recommend）：画像+预警检查+产品推荐+资产配置，一步到位
  ② 画像查询（profile_tool）：查询客户风险画像的四维度得分、C1-C5等级
  ③ 产品推荐（recommend_products）：单独推荐匹配的产品列表
  ④ 资产配置（asset_allocation）：给出资产配置比例建议
  ⑤ 持仓分析（analysis_holdings）：综合MySQL持仓明细+Neo4j行业关系图谱
  ⑥ 客户对比（compare_customers）：对比两个客户的画像、持仓、行业偏好差异
  ⑦ 图谱检索（graphrag_search）：检索知识图谱和向量文档库

这些不是固定的if/elif判断，而是由LLM根据投顾的自然语言问题，自动决定调用
哪个工具、按什么顺序调用、如何组合结果。

3.2 理财顾问给客户推荐产品是怎么跑的？

输入：理财顾问说"给客户张三推荐3款产品，他比较保守"

处理流程：
  第一步：Router Agent意图识别
    识别为 investment_recommendation 意图，置信度0.95+
    → 分发到投顾Agent

  第二步：投顾Agent内部分析
    - 先做投顾子意图分类（product_recommend / portfolio_analysis /
      asset_allocation / comparison）
    - 如果置信度≥0.80，给LLM加意图提示，帮助它更快决策
    - 做跨Session记忆召回：查这个客户之前有没有被推荐过什么、
      历史偏好是什么

  第三步：LLM决策+工具调用
    LLM根据System Prompt（投顾分析师的"人设"）判断：
    "用户说推荐产品，我应该调用 smart_recommend 一键工具"

    → 调用 smart_recommend(customer_id=张三的ID, top_n=3)

    工具内部做了：
      1. 查风控预警（近30天pending状态预警）
      2. 查风评有效期
      3. 查客户画像（ProfileTool → 四维度+熔断+校准）
      4. 综合风险预警和画像等级给出推荐范围
      5. 调用推荐工具匹配产品
      6. 调用配置工具给出资产配比
      7. 返回结构化JSON（画像摘要+预警+推荐列表+配置）

  第四步：LLM生成回复
    LLM读取工具返回的JSON，按回复规范生成Markdown格式的回答：

    > 当前客户推荐正常完成  （状态提示，有异常时才出现）

    ## 风控预警  （有预警时才出现）
    ...

    ## 客户风险画像
    - 风险等级：C3 平衡型
    - 综合评分：75/100
    - ...

    ## 产品推荐
    | 产品名称 | 风险等级 | 预期收益 | 匹配度 | 推荐理由 |
    |---------|---------|---------|-------|---------|
    | XX债券基金 | R2 | 3.5% | 92% | ... |

    ## 资产配置建议
    货币类 15% | 债券类 50% | 混合类 25% | 现金 10%

    > ⚠️ 风险提示：投资有风险，入市需谨慎...

  第五步：SSE流式输出
    投顾角色可以看到LLM逐token实时输出，还能看到工具调用的进度
    （event: token → 逐字输出，event: tool_end → 工具调用完成）

输出：Markdown格式的专业投顾分析报告。

3.3 投顾对比两个客户是怎么跑的？

输入：理财顾问说"比较一下张三和李四的投资画像"

处理流程：
  LLM判断这是 comparison 意图 → 调用 compare_customers 工具
  → ComparisonTool内部：
    1. 分别查张三和李四的画像
    2. 查两人的持仓
    3. 通过Neo4j查两人的行业偏好（知识图谱）
    4. 对比差异：风险等级差异、偏好差异、持仓重叠度
    5. 返回结构化对比报告

输出：两个客户的差异化对比分析。

3.4 投顾分析客户持仓是怎么跑的？

输入：理财顾问说"分析一下张三的持仓情况"

处理流程：
  LLM判断这是 portfolio_analysis 意图 → 调用 analysis_holdings 工具
  → HoldingTool内部：
    1. 从MySQL查持仓明细（产品ID、份额、市值、成本、盈亏）
    2. 分析集中度（单产品占比是否超过阈值）
    3. 从Neo4j查行业关系（该客户的持仓分布在哪些行业）
    4. 计算行业分布图
    5. 标记风险：单产品过度集中、单一行业暴露过大
    6. 返回结构化持仓分析报告

输出：持仓明细、集中度分析、行业分布、盈亏汇总。

3.5 投顾工作台的流式体验

理财顾问在前端使用投顾工作台时，系统走的是 /api/chat/stream/v2（SSE真流式）。

流式事件类型：
  event: meta       → {agent: "advisor", session_id: "..."}
                     前端收到后显示"正在分析..."
  event: tool_end   → {name: "smart_recommend"}
                     前端显示"推荐计算完成"
  event: token      → {content: "为"}
                     逐token显示，投顾看到LLM"一边想一边写"
  event: done       → {reply, recommendations, allocation, ...}
                     完整结果送达

投顾还能看到每个token的实时输出，看到工具调用进度，看到结构化数据的完整
JSON。这对投顾来说非常重要：他知道AI的分析过程，能判断结果是否靠谱。

4.2 理财经理帮客户申购基金是怎么跑的？

输入：理财经理说"帮张三申购10万元的天天利货币基金"

处理流程（这是全系统校验最严格的操作）：

  第一步：LLM Function Calling
    系统Prompt告诉LLM可用工具列表，LLM理解后自动调用：
    purchase_product(customer_name="张三", product_name="天天利货币基金", amount=100000)

  第二步：权限校验
    检查理财经理的角色有没有purchase_product权限

  第三步：解析参数
    - 客户姓名"张三" → 查Neo4j/MySQL → 拿到客户ID
    - 产品名称"天天利货币基金" → 查Neo4j/MySQL → 拿到产品ID
    - 金额100000 → 校验是否合法（>0, ≤1000万上限）

  第四步：P0~P5全量业务校验

    P0-交易时间校验：
      - 是不是交易日？（排除周末和法定节假日）
      - 是不是在交易时间？（9:30-15:00）
      - 如果非交易时间，给出警告但不阻止

    P1-适当性匹配校验：
      - 查客户的C1-C5风险等级
      - 查产品的R1-R5风险等级
      - 匹配：C3可以买R3及以下
      - 如果不匹配，检查是否需要风险揭示（客户C2买R3需要签署风险揭示书）
      - 如果完全不能买（客户C1买R5），直接拒绝

    P2-风评有效期校验：
      - 风评是否存在？不存在→不能操作
      - 风评是否过期（一年有效期）？过期→不能操作

    P3-产品状态校验：
      - 产品是否在售？已下架→不能申购
      - 产品是否暂停申购？

    P4-客户状态校验：
      - 客户账户是否正常？冻结→不能操作

    P5-风控+反洗钱校验：
      - 客户有没有高风险标记？
      - 近30天有没有待处理的风控预警？
      - 单日累计限额检查（当日已交易+本次不能超过200万）
      - 起购金额检查
      - 申购金额倍数检查（必须是100的整数倍）
      - 产品剩余额度检查（募集额度够不够）

  第五步：二次确认（大额交易）
    - 如果申购金额超过1万元，需要理财经理二次确认
    - 系统把待确认信息存入Redis（2分钟有效期）
    - 展示确认摘要："申购：客户张三购买天天利货币基金，金额100000元"
    - 如果金额超过50万，还必须填写备注原因
    - 如果有风险揭示要求，还需要确认风险揭示书

    理财经理回复"确认"（或"确认 备注：客户主动要求"）
    → 系统从Redis取出待确认参数 → 真正执行

  第六步：执行申购
    1. 写入 fin_transaction 表（交易流水）
    2. 更新 fin_holdings 表（持仓变化）
    3. 更新客户余额
    4. 如涉及风险揭示，记录确认信息

  第七步：后置处理链（事件总线自动触发）
    ① 创建审计工单（biz_work_order，自动记录）
    ② 发布事件到Redis Pub/Sub：
       - event:graph_sync → 同步Neo4j知识图谱
    ③ 通过Outbox发布领域事件：
       - transaction.completed → 画像缓存失效 + 投顾风险标记更新

  第八步：更新对话记忆
    保存操作记录到短期记忆和长期归档

输出：
  ✅ 申购成功！
  • 交易流水号: TXN20260727001
  • 产品: 天天利货币基金
  • 金额: 100,000 元
  • 份额: 99,502.49
  • 适用净值日期: 2026-07-27

5.1 风控Agent做什么？

风控Agent（RiskMonitorService）是系统的"安全卫士"。它做的事：

  ① 接收交易事件 → 逐条匹配AML规则 → 生成风控预警
  ② 预警分级（low / medium / high）
  ③ 持久化预警到MySQL + 同步到Redis
  ④ 通过事件总线通知其他Agent（C1/C2/C4联动）
  ⑤ 支持定期调度（每周日凌晨3点自动运行周期校准）
  ⑥ 提供预警查询和管理API

5.2 风控规则引擎怎么跑？

风控监测引擎 RiskMonitorService 内置了一套反洗钱（AML）规则：

  规则评估过程：
    每笔交易事件进来 → 逐条过所有AML规则 → 触发几条规则？
    → 根据规则优先级和触发数量做预警分级

  预警分级逻辑：
    - P1/P2档规则（制裁国、PEP政要、涉赌涉诈、资金归集异常）触发即high
    - P3/P4档规则触发3条及以上 → high
    - P3/P4档规则触发1-2条 → medium
    - 低权重规则触发 → low

  置信度评估：
    ConfidenceCalculator 综合数据完整度、规则触发数量、历史行为来计算
    置信度，标记每条预警的可信程度。

5.3 风控事件联动的完整链路

场景：客户张三申购了80万的高风险基金（触发大额交易规则）

  第0步：业务操作Agent执行申购 → 事务提交成功

  第1步：Outbox写入
    在同一个数据库事务中，写入事件到 outbox 表：
    event_type = "transaction.completed"
    payload = {customer_id: 1001, amount: 800000, ...}

  第2步：Outbox Relay广播
    后台任务扫描 outbox 表 → 发现新事件 → 发布到 Redis "event:agent_domain"

  第3步：多个消费者并行处理

    消费者A（profile-risk-consumer）— 画像风险消费者：
      读取客户1001所有未处理的风控预警
      → 计算最高风险级别
      → 更新 fin_customer_profile.risk_flag 字段
         （无预警→normal，有medium→warning，有high→high）
      → 清除Redis画像缓存 profile:1001
      → 下次投顾查画像时会读到更新后的risk_flag

    消费者B（advisor-risk-consumer）— 投顾风险消费者：
      同样的逻辑
      → 更新Redis risk_flag:1001（TTL 24小时）
      → 下次投顾做推荐时，smart_recommend会先查这个标记
      → 发现risk_flag=high → 推荐范围限制R1-R2

    消费者C（customer-service-risk-consumer）— 客服风险消费者：
      更新Redis cs_risk_ctx:1001
      → 下次客户跟AI客服聊天提到大额操作时
      → 客服Agent读取这个上下文
      → 自动在回复前加上高风险提示
      → 同时维护 risk:alert:pending 集合（供风控管理页查询）

5.4 C1/C2/C4 联动机制

这是项目架构评审的核心亮点之一：

  C1 联动 — 投顾降权：
    风控预警产生后 → 投顾Agent在推荐产品时自动限制范围
    - high → 只能推荐R1-R2
    - medium → 只能推荐R1-R3
    - normal → 正常推荐
    这是"自动降权"，不需要人工介入。

  C2 联动 — 风控监测日志：
    所有交易事件都记录到风控日志中
    → 风控管理页可以实时看到风险事件流
    → 供风控专员监控和分析

  C4 联动 — 客服风控提示：
    当有风控预警的客户跟AI客服对话时：
    - 客服Agent检测到敏感操作关键词（大额转账、大额赎回等）
    - 自动查询Redis中的客服风险上下文
    - 在回复中自动附加风控提示：
      "⚠️ 风控提示：您的账户当前处于高风险关注状态..."
    - 同时Router Agent在路由阶段也会做风控预检
      （有预警客户+敏感操作 → 强制走客服Agent路径）

5.5 风控定时任务

系统启动时自动启动两个调度器：

  调度器1 — 风控周期校准：
    每周日凌晨3点运行
    → 扫描所有客户的画像和近期交易
    → 重新计算风险标记
    → 更新画像状态
    （由 risk_scheduler.py 管理）

  调度器2 — 图谱同步重试：
    每60秒运行一次
    → 扫描之前同步Neo4j失败的操作
    → 自动重试（最多3次）
    （由 graph_sync_retry_service.py 管理）

5.6 风控管理前端页面

风控专员在前端有专门的"风控管理"页面：
  - 查看所有风控预警列表
  - 按客户/等级/状态筛选
  - 处理预警（标记为处理中/已解决/误报）
  - 处理结果触发新一轮事件广播
  - 预警状态变更 → 自动更新画像风险标记 → 恢复推荐范围

6.1 数据分析Agent做什么？

数据分析Agent（NL2SQLService）让业务人员可以用自然语言直接查询数据库。

核心能力：
  ① 自然语言→SQL生成→执行→结果解读（一条龙服务）
  ② BI仪表盘（6大指标实时聚合展示）
  ③ 分析洞察产生后，安全地联动投顾和风控

6.2 NL2SQL的完整流程

输入：风控专员问"统计近30天各等级风险预警数量"

  第零层：快速预检
    判断输入是不是数据查询意图
    - 纯问候语（"你好"）→ 拒识，引导用户提业务问题
    - 非查询意图（"写诗"）→ 拒识
    - 无业务关键词+短输入 → 拒识

  第一层：动态Schema选择
    从用户问题中提取关键词匹配相关数据库表：
    - "风险预警" → fin_risk_alert
    - 同时补充外键关系信息（帮助LLM写JOIN）

  第二层：LLM生成SQL
    组装上下文：选中的表结构DDL + 表关系 + Few-shot示例
    → 送给LLM → LLM生成SQL：
    SELECT alert_level, COUNT(*) as cnt
    FROM fin_risk_alert
    WHERE create_time >= DATE_SUB(NOW(), INTERVAL 30 DAY)
    GROUP BY alert_level

  第三层：SQL安全校验（五道闸门）
    闸门1-意图预检：已通过
    闸门2-最小Schema：已应用
    闸门3-只读校验：
      - 剥离所有SQL注释（防止注释绕过）
      - 必须SELECT开头（拒绝UPDATE/DELETE/INSERT/DROP/ALTER）
    闸门4-危险语法拦截：
      - 禁止UNION、INTO、LOAD_FILE、EXEC、EXECUTE
      - 禁止多语句（分号后面还有内容）
    闸门5-敏感数据和资源边界：
      - 禁止查询password/api_key/token/id_card等敏感列
      - 最多返回100行
      - SQL执行结果再做二次脱敏

  第四层：执行SQL
    用同步数据库连接执行（避免污染异步事务）
    → 获取结果 → 过滤敏感列的值 → 返回

  第五层：LLM解读结果
    把查询结果送给LLM，生成自然语言解释：
    "近30天共产生15条风控预警，其中高风险3条、中风险8条、低风险4条..."

  第六层：Redis缓存
    按 user_id + SQL的MD5 做缓存key
    → 相同问题10分钟内直接返回缓存（默认TTL=600秒）
    → 减少重复LLM调用和数据库查询

输出：
  {
    sql: "SELECT ...",
    query_result: [{alert_level: "high", cnt: 3}, ...],
    explanation: "近30天共产生15条风控预警...",
    safety: {select_only: true, ...},
    timing: {generate_ms: 450, execute_ms: 23, explain_ms: 1200}
  }

6.3 BI数据分析仪表盘

前端独立页面，基于Vue 3 + ECharts，从数据库实时聚合数据：

  仪表盘六类指标：
    ① 客户AUM分布 — 按资产区间统计客户数量（高价值客户识别）
    ② 风险收益对比 — 不同风险等级产品的平均收益+数量
    ③ 热销产品 — 按交易量排序的产品列表
    ④ 月度交易趋势 — 申购/赎回/转账的月度变化曲线
    ⑤ 风险预警分布 — 按等级和状态统计预警数量
    ⑥ 产品货架矩阵 — R1-R5 × 产品类型的分布热力图

6.4 分析洞察白名单（安全联动）

这不是所有的NL2SQL查询结果都能去影响投顾或风控！系统设计了严格的白名单：

  只有满足以下条件才能产生分析洞察：
    1. 查询结果中同时具有 customer_id 和数值证据
    2. 只能提取两类可验证事实：
       - 持仓回撤 > 10%
       - 单周交易次数 ≥ 10次，且有对应金额证据

  洞察产生流程：
    查询结果 → InsightExtractor提取 → 校验白名单 → 包装为 analytics_insight领域事件
    → 进入事务Outbox → Redis广播 → 画像和风控消费者订阅

  边界保护：
    - 分析洞察绝不直接修改客户正式的C1-C5风险等级
    - 正式评级必须走风评问卷→规则引擎→校准→审计的完整流程
    - 洞察事件只能作为投顾约束或风控监测的输入

6.5 分析结果的数据脱敏

所有查询结果在返回用户前都要经过脱敏处理：
  - 手机号：138****5678
  - 邮箱：ab***@domain.com
  - 密码/Token/身份证等敏感列直接过滤掉

第七章  客户画像系统深度解析
═══════════════════════════════════════════════════════════════════════════════

7.1 画像系统包含什么？

客户画像（Customer Profile）是整个系统的核心数据，它驱动了投顾推荐、产品
适当性匹配、风控评估等关键业务。

画像的构成：
  (1) 四维度评分系统
      - 基础属性维度（年龄、收入、学历、职业等客观信息）
      - 投资经验维度（投资年限、历史产品类型、交易频率、历史收益）
      - 风险偏好维度（风险测评等级、可承受亏损、投资目标）
      - 行为特征维度（交易频率变化、行为一致性）

  (2) 熔断规则（5条）
      触发条件举例：
      - 80岁以上+高风险产品 → 熔断
      - 年收入不足+大额投资 → 熔断
      - 投资经验不足+复杂产品 → 熔断

  (3) 特殊场景处理
      - 60岁以上退休人群 → 自动偏向保守
      - 高净值人群 → 风险容忍度适当放宽

  (4) 行为校准
      - 实际交易行为与风评问卷不一致 → 下调权重
      - 频繁交易 → 调整风险判断

  (5) 置信度计算
      综合数据完整度、数据来源、信息新旧来计算

7.2 画像研判的完整流程

触发方式：
  - 手动触发：客户完成风评问卷后 → 自动触发研判
  - 自动触发：smart_recommend发现画像缺失时 → 自动修复研判
  - 周期触发：每周日风控调度器 → 批量重新研判

研判流程：
  第一步：收集客户数据
    - 从fin_risk_assessment取最新风评结果
    - 从sys_user取基本信息
    - 从fin_transaction取交易数据
    - 从fin_holdings取持仓数据
    - 从fin_customer_profile取历史画像

  第二步：四维度计算
    DimensionCalculator 分别计算四个维度的得分（0-100分）
    - 每个维度有若干子项
    - 子项根据客户实际数据打分
    - 各子项加权求和 → 维度得分

  第三步：熔断检查
    CircuitBreaker 逐条检查5条熔断规则
    → 如果触发：记录警告，限制后续推荐范围

  第四步：特殊场景处理
    SpecialCaseHandler 检查特殊场景
    → 如果是特殊场景，调整得分

  第五步：行为校准
    BehavioralCalibrator 检查实际行为与风评的一致性
    → 实际比风评激进 → 适当降低风险容忍度得分
    → 实际比风评保守 → 适当提高风险容忍度得分

  第六步：总分计算
    四维度得分 → 加权求和 → 归一化0-100
    → map_score_to_risk_level → C1-C5等级

  第七步：置信度计算
    数据完整度（缺失字段比例）
    + 数据来源权重（问卷>行为>推断）
    + 信息新鲜度（风评是否过期）
    → 综合置信度0-1

  第八步：持久化
    1. 更新 fin_customer_profile 表
    2. 更新 CustomerTag 表（风险偏好标签）
    3. 失效Redis缓存 profile:{customer_id}
    4. 同步Neo4j知识图谱
    5. 发布画像更新事件 → 通知投顾和客服Agent

7.3 画像的Cache-Aside策略

  读取画像时：
    1. 先查Redis缓存 profile:{customer_id}
    2. 命中 → 直接返回
    3. 未命中 → 查MySQL → 写入Redis（带TTL）→ 返回

  更新画像时：
    1. 更新MySQL
    2. 删除Redis缓存
    3. 发布 profile_update 事件
    4. 下次读取时自动重建缓存

8.1 知识库包含什么？

  - 金融产品知识文档（PDF/文本）
  - 业务规则和政策文件
  - FAQ常见问题库
  - 产品说明书

8.2 知识入库流程

  管理员上传文档 → MinIO存储原始文件
  → DocumentParser解析内容
  → EmbeddingTool生成向量（Ollama Embedding）
  → 存入Milvus向量数据库
  → 同时记录元数据到MySQL fin_knowledge_meta表

8.3 RAG检索流程（客服Agent内）

  用户提问 → EmbeddingTool把问题也转成向量
  → 在Milvus中做相似度搜索
  → 返回Top K个最相关的文档片段
  → RerankerTool做重排序（提升精准度）
  → 把片段+来源信息组装成上下文
  → 送给LLM生成回答

8.4 知识图谱（GraphRAG）

  Neo4j存储的是实体和关系：
    - 客户节点 → 属性：风险等级、资产规模
    - 产品节点 → 属性：风险等级、类型、收益
    - 行业节点 → 关系：产品属于哪些行业
    - 关系：客户-持有→产品，客户-类似→客户，产品-属于→行业

  GraphRAG检索：当投顾问"新能源行业有什么产品"时，
    1. 在Neo4j中查询"新能源"行业节点
    2. 沿着关系找到属于该行业的产品
    3. 同时用向量搜索在文档库中找新能源相关分析
    4. 合并图谱结果和文档结果

9.1 认证和授权

  JWT Token认证（中间件层）：
    每个请求必须携带有效JWT
    → JWTAuthMiddleware解析Token → 提取user_id和role
    → 注入到request上下文中
    开发阶段支持AUTH_MOCK_MODE=true跳过认证

  RBAC角色权限：
    客户 / 理财顾问 / 客户经理 / 风控专员 / 管理员
    → 每个角色有不同的API和工具访问权限

9.2 输入安全过滤

  InputSafetyFilter检查用户输入：
    - 恶意内容检测
    - SQL注入尝试检测
    - Prompt注入尝试检测
    → 被拦截的内容直接返回block，不会送给LLM

9.3 输出安全审核

  SafetyService检查LLM输出：
    - 合规性检查（是否给出具体买卖建议？）
    - 内容质量检查（是否编造数据？）
    - 敏感信息检查（是否泄露客户隐私？）
    → 不通过则替换为安全回复

9.4 金融合规要求

  - 所有产品推荐必须附风险提示
  - 适当性匹配必须校验
  - 风评有效期一年，过期提示重做
  - 大额操作需要二次确认
  - 所有操作自动生成审计工单
  - 可疑交易自动上报

9.5 隐私保护

  - 客户只能查看自己的信息
  - 联系方式自动脱敏显示
  - 分析查询结果脱敏
  - 敏感列完全过滤

第十二章  Agent通信方式总结
═══════════════════════════════════════════════════════════════════════════════

12.1 同步调用（Router分发）

  Router Agent 直接 import 各业务Agent，调用其方法，等待返回。
  适用场景：用户主动发起请求，需要即时回复。

  示例链路：
    用户 → Router Agent → AdvisorAgent.execute()
    → smart_recommend工具 → 返回结果
    → Router Agent → 用户

12.2 异步事件（Event Bus）

  业务操作完成后通过Redis Pub/Sub发布事件，各Agent独立消费者订阅。
  适用场景：一个操作需要通知多个Agent，且不需要等待它们处理完。

  事件可靠性保证三层机制：
    ① Outbox事务写入：事件在业务事务中一起写入MySQL
    ② Relay定时广播：后台任务每秒读取Outbox，发布到Redis
    ③ 幂等消费账本：每个消费者有event_id+consumer的唯一记录，防重复

12.3 共享存储（Redis缓存）

  多个Agent通过Redis共享状态：
    - 风控Agent写 risk_flag:客户ID → 投顾Agent读
    - 风控Agent写 cs_risk_ctx:客户ID → 客服Agent读
    - 画像Service写 profile:客户ID → 投顾Agent/客服Agent读

12.4 数据库共享（画像表）

  所有Agent共享 fin_customer_profile 表：
    - 风评Service写 risk_level_code
    - 风控Agent写 risk_flag
    - 投顾Agent/客服Agent/客户账户Agent读
