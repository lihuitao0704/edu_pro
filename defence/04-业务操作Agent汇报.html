一句结论

自然语言可以发起业务，但绝不能绕过权限、确认和风控

`operator_agent.py` 将 NL2API 与受控工具注册表结合，把申购、赎回、转账、工单和查询转化为可验证、可审计的业务操作。

核心结论：我将自然语言转成受控业务动作，而不是直接执行命令。每一次申购、赎回或转账都必须经过权限、参数、适当性、状态和二次确认等 P0-P5 校验。

答辩重点：模型只提出调用意图

LLM Function Calling 负责识别工具与提取参数；客户、产品和金额需再次解析为业务实体，RBAC 和规则链路拥有最终执行权，因此自然语言不会绕过系统边界。

亮点与边界

P0-P5 将交易时段、适当性、风评有效期、产品状态、资金与确认链拆开校验。任一硬性条件不满足即停止执行，并保留原因、操作人和审计记录。

自然语言指令 “为张三申购…”
→
参数提取 客户、产品、金额、动作
→
身份 / 权限 RBAC 与客户归属校验
→
P0-P5 校验 适当性、时间、额度、AML、状态
→
二次确认 敏感操作写入 Redis 待确认状态
→
执行与审计 交易/工单落库、发布领域事件

当前实现：工具注册表使操作能力可扩展；确认状态、审计记录和事件发布使每次执行可追溯。

覆盖的业务动作

申购、赎回、转账、重新风险评估、联系信息更新、可疑交易上报、工单创建，以及产品/持仓/客户全景查询。

为什么先校验

资金与客户状态一旦变化难以回滚；系统优先校验风险等级、产品状态、持仓余额、交易时段和日累计限制。

联动价值

成功操作发布交易事实；高风险或可疑操作触发风控预警，从而驱动画像、投顾、客服的后续状态。

NL2API：让一句话业务办理可控可审计

需求映射：需求文档要求 NL2API 覆盖申购、赎回、转账、信息变更等标准业务接口，并强制权限校验、二次确认和工单留痕。当前实现把自然语言理解限定在工具注册表和明确参数内，模型不能绕过业务校验直接修改资金或客户状态。

为什么必须二次确认

金融操作具有不可逆成本。系统将意图识别与最终执行分离：先显示金额、产品、客户、风险提示与交易要素，再由确认令牌触发真正的 API 调用，降低误操作与越权风险。

为什么必须审计

每次工具调用都可以对应用户、角色、参数、校验结果、执行结果和领域事件。发生争议时，能够沿着“自然语言—工具—规则—落库”链路回放，而不是依赖聊天记录猜测。
