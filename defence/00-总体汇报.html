业务结论

把财富服务的“判断、建议、执行、守护”串成可控闭环

平台以统一对话入口承接多角色需求，Router 与编排层将请求分派给六类 Agent；规则、数据与知识底座保证业务过程可解释、可审计、可持续演进。

核心结论：我将系统设计为“统一路由、专业分工、事件联动、全程留痕”的金融服务链路。Multi-Agent 的价值不在数量，而在每项能力都能被复用、被追溯、被约束。

统一路由

Router Agent 只负责识别意图、校验角色和分发请求，不承载具体业务判断；这样既避免单个 Prompt 膨胀，也让客服、投顾、风控和操作能力各自保持清晰边界。

亮点与边界

LLM 用于理解、编排和解释，权限、规则、业务事实与审计留痕仍由系统控制。系统追求的不是“自动做更多”，而是在金融边界内稳定地做对。

6 类

专业 Agent

客服、画像、投顾、风控、数据分析、业务操作在统一口径下协作。

5 类

数据与知识基础设施

业务事实、会话缓存、关系推理、语义检索与文件知识各司其职。

1 条

统一服务链路

HTTP/SSE 请求经 API、路由与编排，交付结构化、可追溯的结果。

项目主流程

Vue 3 前端 客户对话、顾问工作台、风控与运营页面
→
FastAPI 统一 API、身份边界、HTTP / SSE
→
Router + 编排 六类意图识别、风险预检、统一响应
→
业务 Agent 客服 / 画像 / 投顾 / 风控 / 分析 / 操作
→
服务与底座 规则、工具、MySQL、Redis、Neo4j、Milvus、MinIO

当前实现：`main.py` 提供入口；`unified_chat.py` 与 Router/ChatOrchestrator 统一承接自然语言服务。

技术栈：为什么这样组合

应用与智能层

  • Python + FastAPI：异步 API 与 SSE 流式反馈
  • SQLAlchemy Async：业务数据访问
  • LangChain + OpenAI 兼容 SDK：工具调用和模型编排
  • Pydantic：输入输出契约与参数校验

体验与数据层

  • Vue 3 + TypeScript + Vite：企业级交互界面
  • Pinia、Element Plus、ECharts：状态、组件和看板
  • MySQL / Redis：事实数据、缓存和会话
  • Neo4j / Milvus / MinIO：关系、语义和文档知识

六类 Agent 的分工

客服 / 画像

回答与理解客户；沉淀画像、偏好与短期行为信号。

投顾 / 风控

在适当性约束内生成建议；通过规则、预警和工单守住边界。

操作 / 分析

把自然语言转为受控业务办理或只读数据洞察。

总结：AI 负责理解与编排，规则负责确定性约束，数据底座负责事实与记忆——三者共同构成金融服务的可信闭环。

从需求到交付：我们完成了什么

需求映射：需求文档要求以五阶段建设客服/RAG、画像/NL2SQL、图谱/投顾/业务操作、风控/记忆和系统集成。当前系统已将这些能力纳入 FastAPI + Vue 3 的统一平台，并通过 Router、ChatOrchestrator 和领域事件连接为可演示闭环。
P1 · 服务入口客服问答、知识库与统一 API
P2 · 认知能力画像研判、适当性与 NL2SQL
P3 · 决策执行GraphRAG 投顾与 NL2API 操作
P4 · 控制底座预警、工单、五层记忆
P5 · 集成呈现多 Agent 联动与角色化工作台

领导可见的业务价值

把原本分散在客服、顾问、风控、运营和 IT 的工作，压缩为“一个入口、多个专业 Agent、统一留痕”的服务链路；既提升响应效率，也让关键决策有据可查。

答辩可讲的工程亮点

我们不是只展示大模型对话：RAG 给出处，GraphRAG 连接关系，NL2SQL/NL2API 将自然语言转为受控动作，规则引擎和事件总线把合规与协作嵌入主链路。
