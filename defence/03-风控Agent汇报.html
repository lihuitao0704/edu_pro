一句结论

将风险判断前置到资金变化之前，并将结果传递给全链路

风控能力由规则引擎、交易流程服务、风险监控服务和预警工单组成：既控制单笔操作，也为投顾、画像与客服提供一致的动态风险状态。

核心结论：我把风控设计成风险闭环：从规则识别、预警生成到处置反馈和审计留痕连续发生。动态信号可以约束推荐、触发核验和提示客服，但不能绕过测评流程直接修改正式风险评级。

答辩重点：事前拦截与事后联动分层

交易前由适当性、额度、AML 和账户状态等规则决定“能不能做”；交易后或定时分析形成风险事件，通过事件总线通知画像、投顾与客服决定“谁需要知道”。

亮点与边界

预警是待核验的业务信号，不等于最终裁决。C1-C5 等正式风险评级必须经过风评问卷、规则引擎、校准和审计，避免模型或单次行为数据越权改写合规事实。

交易请求 申购、赎回、转账、可疑上报
→
事前评估 适当性、额度、状态、时间、AML
→
决策 允许 / 人工复核 / 拦截
→
风险预警 规则命中、等级、状态、证据
→
工单与联动 处理闭环、投顾约束、客服提示

当前实现：`TransactionFlowService` 和 `RiskMonitorService` 将交易上下文、规则检测、预警持久化与工单处理串联。

确定性规则引擎

  • 四维画像评分：基础、经验、风险偏好、行为
  • 熔断与特殊场景处理
  • 风险等级映射、置信度与适当性矩阵
  • 预警生命周期及处理状态
关键边界

动态约束 ≠ 正式风险等级

预警可将 `risk_flag` 同步为投顾推荐约束、客服风险提示和画像动态状态；正式 C1-C5 等级仅由风险评估/画像研判流程变更。

金融合规红线如何被编码

需求映射：需求文档要求适当性匹配、反洗钱规则、分级预警、风险画像和三层记忆，并明确 C1 客户不能购买 R4/R5 产品。当前实现将这些要求前置为交易闸门、产品匹配、熔断规则和预警工单，而非只在页面弹出风险提示。

从抽查到逐笔控制

金额、产品状态、客户状态、持仓余额、交易时间、日累计限额、风险标记与可疑交易等条件进入操作前校验；高风险请求不会先成交、后补救。

从单点预警到协同处置

预警事实可经 Event Bus 投递给画像、投顾和客服：画像更新动态信号，投顾收紧建议，客服生成审慎沟通提示；风控专员通过工单完成处置和闭环。
