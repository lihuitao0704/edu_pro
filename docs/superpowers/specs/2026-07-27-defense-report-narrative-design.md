# 答辩汇报页面叙事化改造设计

## 目标

将现有金融智能财富管家汇报页改造为一条可连续讲解的答辩主线。各页从答辩者角度陈述业务价值、实现证据与金融边界，避免把同一亮点重复写在多个页面。

## 页面与导航

页面顺序固定为：

`00-index.html`（目录）→ `00-总体汇报.html` → `01-投顾Agent汇报.html` → `02-客服Agent汇报.html` → `03-风控Agent汇报.html` → `04-业务操作Agent汇报.html` → `05-数据分析Agent汇报.html` → `06-多Agent联动与架构汇报.html` → `07-记忆架构汇报.html`。

目录页只作为入口。其余八页顶部统一只保留“上一页”和“下一页”两个导航项：总体页的上一页回目录，记忆架构页的下一页回目录。页内页尾也使用相同的下一页目标，避免导航断链。

## 叙事边界

每页以简约的答辩结构组织，不使用“我会这样讲”标题：

1. 首屏给出该页面的核心结论，使用第一人称答辩语气。
2. 现有流程图承担输入、处理、输出的说明，不重复逐字稿的每一步细节。
3. 补充“亮点与边界”或等价的简短标题，说明可验证实现、合规约束和不做什么。
4. 引用代码/需求/逐字稿中的真实能力，不将规划项表述为已上线能力。

## 各页唯一职责

| 页面 | 核心问题 | 独有重点 |
| --- | --- | --- |
| 总体 | 为什么需要 Multi-Agent | 统一路由、角色隔离、总体价值与技术底座 |
| 投顾 | 如何把策略主动找到适合的客户 | 七工具编排、smart_recommend、风评缺失降级 |
| 客服 | 如何可靠回答并服务客户 | RAG、会话召回、C4 风险提示、转人工兜底 |
| 风控 | 如何发现并闭环处置风险 | 规则、预警、工单、动态约束与审计 |
| 业务操作 | 如何让自然语言变成受控业务动作 | NL2API、RBAC、P0-P5 校验、二次确认 |
| 数据分析 | 如何让数据洞察安全参与协同 | NL2SQL 五道闸门、BI、洞察白名单、Outbox |
| 多 Agent | 如何让多个专业能力可靠协作 | Router、Outbox、Redis、幂等消费、Trace |
| 记忆架构 | 如何长期理解客户且不混淆事实 | Redis/MySQL/Milvus/Neo4j 分层、读取与写入闭环 |

## 验证

更新静态报告测试，确保：

- 页面顺序中的所有链接都存在；
- 每个专题页具有且只具有“上一页”“下一页”顶部导航；
- 原 `index.html` 与 `记忆架构.html` 不再被页面引用；
- 原有的需求映射、流程图和重点能力锚点仍然存在。

## 自检

本设计没有待定项；替代文件名、页面顺序、叙事口径和导航终点均已明确。页面不新建业务能力，仅重新组织和补充现有实现的答辩表达。
