# Four-Store Test Data Refresh Design

## Goal

Refresh only the project databases selected by the current environment configuration. Preserve all schemas, indexes, constraints, and application configuration while creating a coherent test dataset.

## Scope

- MySQL: clear data from every project application table and repopulate every table with at least 100 rows.
- Neo4j: clear all nodes and relationships in the configured graph database, then rebuild graph records and relationships from the new MySQL dataset.
- Redis: clear only the configured Redis logical database. Do not repopulate it; runtime caches are regenerated by the application.
- Milvus: do not connect to, delete from, alter, or insert into any Milvus collection.

## Safety Boundaries

1. The refresh script loads all target names only from `app.config.settings.get_settings()` and prints a redacted target summary before mutating anything.
2. The script refuses to run without an explicit `--confirm` flag.
3. It performs read-only preflight checks for connectivity, target database names, MySQL table inventory, Neo4j access, and Redis DB selection before issuing any delete statement.
4. MySQL truncation/deletion is ordered to respect foreign keys. If a table cannot be populated with at least 100 rows, the script reports failure rather than silently succeeding.
5. The script never executes `FLUSHALL`; Redis cleanup uses `FLUSHDB` against the configured logical DB only.
6. The script does not import or instantiate the Milvus client.

## Dataset

The generator is deterministic and uses synthetic, non-production identities. It creates at least 100 customers, products, profiles, risk assessments, holdings, transactions, alerts, recommendations, work orders, conversation records, and supporting rows required by every mapped MySQL table. Junction and event tables receive more than 100 rows where needed to preserve relational realism.

All graph source IDs come from the newly inserted MySQL rows. Neo4j includes customer, product, industry, risk-level, and supporting nodes, plus customer-product holding, product-industry, customer-risk, and other relationships supported by `scripts/neo4j_import.py`.

## Execution Flow

1. Discover and print target inventories and current counts.
2. Abort before mutation if a required connection or target identity check fails.
3. Clear MySQL table data in dependency-safe order and write the deterministic dataset in a transaction-aware sequence.
4. Clear the selected Redis DB.
5. Clear configured Neo4j graph data and rebuild it from MySQL.
6. Verify each MySQL application table has at least 100 rows; verify Redis DB is empty; verify Neo4j has nodes and relationships corresponding to the generated customers and holdings.
7. Print a machine-readable and human-readable summary. A failed verification produces a non-zero exit code.

## Non-Goals

- No schema migration, index change, service configuration change, or Milvus modification.
- No mutation of databases or Redis logical DBs outside the targets selected by the project configuration.
