# 投顾 Agent 答辩页面优化设计

## 目标

将 `01-投顾Agent汇报.html` 优化为理财顾问模块的独立答辩页。页面以“从人找策略到策略找人”为主线，完整解释客户推荐从请求进入、约束形成、工具编排、结果展示、业务承接到事件/记忆回写的流程。

## 页面结构

1. **核心价值**：以第一人称说明将顶级投资经理的分析框架模型化，输出千人千面的可解释建议。
2. **完整流程架构图**：使用现有离线 HTML/CSS 流程图样式，展示：
   `理财顾问/客户需求 → Router Agent → 客户身份与会话记忆 → 风评/画像/持仓/预警约束 → AdvisorAgent 七工具编排 → smart_recommend → 产品推荐/资产配置/预算建议 → 合规与业务操作承接 → Outbox/Event Bus → Profile/Redis/MySQL/Neo4j 回写`。
3. **七工具分工**：`smart_recommend`、`profile_tool`、`recommend_products`、`asset_allocation`、`analysis_holdings`、`compare_customers`、`graphrag_search`。
4. **关键保护机制**：客户身份验证；缺失画像或过期风评的测评提示和 C1/R1 降级；动态预警限制可推荐风险范围；推荐与正式交易分离。
5. **需求文档与当前实现对照**：标明基础需求（画像、推荐、资产配置、GraphRAG）和当前项目工程化增强（七工具编排、组合式 smart_recommend、预算分配、角色化叙事、SSE 工具进度、Outbox 回写）。
6. **答辩亮点与边界**：投顾是解释者和编排者；适当性、正式风险评级和交易确认由规则/业务链路掌控。

## 表述边界

- 只陈述已在项目代码、逐字稿或现有报告中能够对应的能力。
- 页面不宣称投顾 Agent 直接执行交易，也不称模型能单独修改 C1-C5 正式风险评级。
- 对“不同于需求文档”的内容使用“当前工程增强”表述，不将其描述为新增监管能力。

## 验证

扩展 `tests/test_report_html.py`，验证投顾页面同时包含完整流程图、七工具、需求对照、工程增强和业务边界关键字；保留已有“画像缺失 / 风评过期”“低风险产品”等保护机制测试。

## 自检

本页只优化投顾报告及其静态测试，不改变其他 Agent 页面、导航链路或后端业务实现；流程使用现有离线 HTML 组件，不增加外部依赖。
