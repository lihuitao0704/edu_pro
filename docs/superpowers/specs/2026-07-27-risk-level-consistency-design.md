# 风险等级数据一致性整改设计

## 目标

将客户风险等级统一为唯一的代码—名称对，彻底消除 `C1`—`C5` 与中文标签混存、画像和评估结果错配，以及新增 Agent 绕过标准化逻辑直接写库的问题。

唯一标准如下：

| code | name |
| --- | --- |
| C1 | 保守型 |
| C2 | 稳健型 |
| C3 | 平衡型 |
| C4 | 积极型 |
| C5 | 激进型 |

历史输入 `进取型` 仅作为 `C4` 的兼容别名。标准化结果、数据库数据、API 响应、前端展示和新文档均不得再输出 `进取型`。

## 已确认事实与根因

- 现有数据库中，`fin_customer_profile.risk_level` 同时保存中文名称与 C 编码；`fin_risk_assessment.risk_level` 保存 C 编码。
- 当前最近评估与画像等级不一致 98 条。根因是问卷服务、画像服务、校准趋势服务和种子脚本各自写入等级，而不是通过共同的写入边界。
- 画像服务的四维计算结果可覆盖画像等级，但没有同步同一笔评估记录；前端再用本地映射容忍两种格式，掩盖了数据错误。

## 方案选择

不采用“继续保留旧字段并在读取时兼容”的方案，因为它会保留未来混存入口；也不采用前端转换修复，因为它只能掩盖展示污染。

采用强约束统一模型：数据库保存规范 code/name 对，所有领域服务经单一标准化和写入服务持久化，Agent 只产出代码。

## 领域模型与标准化

新增 `app/config/risk_level_mapping.py`，作为全项目唯一映射源，提供：

- `RiskLevelCode`：仅允许 `C1`—`C5`。
- `NormalizedRiskLevel`：不可分割的 `{risk_level_code, risk_level_name}` 结果。
- `normalize_risk_level(value)`：接受标准 code、标准中文名和历史别名 `进取型`；去除首尾空格并忽略 code 大小写；未知值抛出明确的领域校验错误。
- `risk_level_from_score(score)`：根据既有分档生成规范结果，替代散落的 code/name 映射。

运行时内存、Agent 契约、适当性计算、图谱同步和风险评分记录均使用 `risk_level_code`。中文名只在 API 展示模型、前端和面向用户的文本中出现，且必须由规范 code 推导，不能由 Agent 自由生成。

## 持久化与一致性边界

新增专用的风险画像写入服务，作为 `fin_risk_assessment` 和 `fin_customer_profile` 的唯一等级写入入口。

提交问卷时，服务先保留问卷原始得分和答案；再计算四维最终得分和最终风险 code；最后在同一数据库事务内完成：

1. 向 `fin_risk_assessment` 写入最终 `total_score`、规范 code 和原始问卷证据。
2. 向 `fin_customer_profile` 写入相同的 `risk_level_code`、由 code 推导的 `risk_level_name`、相同的最终风险分和四维分数。
3. 同步画像 JSON、风险偏好标签、缓存失效和图谱事件，其中结构化数据只使用 code。

校准趋势调整也必须调用该服务，不能直接赋值画像字段。若调整等级，评估历史新增一笔带 `trigger_type=auto_calibration` 的审计记录，并把画像更新为该笔最终等级。

这样每个客户的画像始终对应最新评估记录；任意画像四维分数之和等于画像风险分，且风险分落在其 code 的规定分档内。

## 数据库迁移

新增可重复执行的迁移，按以下顺序实施：

1. 为 `fin_customer_profile` 新增 `risk_level_code VARCHAR(2)` 与 `risk_level_name VARCHAR(8)`。
2. 用 code、五个标准中文名和历史别名回填两列；发现未知值时迁移失败并输出记录，不执行删除。
3. 为 code 和 name 添加非空约束及五组合法配对的 `CHECK` 约束。
4. 应用服务全部切换到新列后删除旧 `risk_level`，使任何直接覆盖旧字段的代码立即失败。

`fin_risk_assessment.risk_level` 保留，含义固定为 C1—C5，并增加 code 集合约束。产品表 `fin_product.risk_level` 保持 R1—R5，不属于本次客户风险等级字段迁移。

## 历史重建与数据安全

新增显式执行的重建脚本，只影响 `fin_risk_assessment` 与 `fin_customer_profile`。

脚本先读取所有两表记录并在内存中生成重建快照：以每个客户最新有效评估为优先来源，兼容历史 code、中文名和 `进取型`；用最终 code 对应的可验证风险分与四维分数重建。画像存在而没有可归一化评估的记录会在删除前被报告为错误，整个操作退出且不清空表。

验证通过后，脚本在单次受控运行中清空且仅清空这两张表，按原 `customer_id` 写回一致记录，并验证：

- 两表同一客户的最新等级 code 一致；
- 画像 code/name 是合法配对；
- 四维分数合计等于风险分；
- 风险分符合 C1—C5 的分档。

脚本必须要求 `--apply --confirm-reset-risk-profile-data` 双参数，默认只打印预检报告，不会修改数据库。

## API 与前端契约

客户画像、风险评估、适当性校验、投顾上下文和图谱同步接口改用明确字段：

```json
{
  "risk_level_code": "C3",
  "risk_level_name": "平衡型"
}
```

不再返回或接受客户风险语义的模糊 `risk_level` 字段。产品风险字段仍使用其既有 `risk_level: "R3"` 契约，并以类型和接口文档区分产品风险与客户风险。

前端类型改为显式 code/name；展示只读取 name，适配产品等级、色彩和图表只读取 code。删除前端的中文/code 兼容映射，避免脏数据被静默展示。

## 防回归措施

- Agent Prompt 明确规定仅输出 `risk_level_code`，解析器只接受标准 code 后再进入标准化。
- Pydantic 模型验证 Agent 和 API 边界；无效 code 或中文输入返回校验错误。
- 数据库 `CHECK` 约束阻止 code/name 错配、名称列写入 C 编码和不合法 code。
- 自动化测试覆盖标准化、单一写入服务、问卷流程、校准流程、API 契约、迁移预检及历史重建后的跨表和四维一致性。
- 新增静态守卫测试，禁止 `FinCustomerProfile` 在统一写入服务以外直接赋值风险等级字段。

## 非目标

- 不改变产品风险等级 R1—R5 的定义或适当性业务规则。
- 不把 AML 的 high/medium/low 预警等级纳入客户投资风险等级映射。
- 不以历史中文展示文本改写非结构化知识库；仅修正含客户风险等级标准定义的配置、Prompt、种子数据和前端文案。
