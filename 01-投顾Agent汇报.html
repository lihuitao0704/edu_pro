答辩核心价值

从“人找策略”到“策略找人”

我们将顶级投资经理的分析框架模型化，通过 AI 实现“千人千面”的个性化资产配置：把复杂的市场波动转化为稳健的财富增长方案，让专业投资服务触手可及。

核心结论：我把投顾的工作从“人找策略”推进到“策略找人”。LLM 负责在七类工具之间编排，画像、风评、预警和适当性规则共同决定推荐范围，而不是让模型凭一句话给出买卖结论。

答辩重点：一次编排完成全链路

smart_recommend 将画像查询、风险预警、产品匹配与资产配置合并为一次受控工具调用，降低多轮调用延迟，也保证各步骤使用同一份客户约束。

亮点与边界

推荐结果是可解释建议，不是交易指令。若画像缺失或风评过期，系统先提示测评并降级至低风险产品；正式购买仍需业务操作 Agent 的合规校验与确认。

我们解决什么

让专业判断规模化，而不是让模型替代合规

过去是顾问在产品、行情和客户资料中寻找策略；现在由 AdvisorAgent 先识别客户约束、持仓缺口与产品适配，再把可解释的候选策略推给正确的人。

我们如何做到

“千人千面”来自事实、规则与知识的组合

画像、持仓、风险等级、产品适当性、市场知识和反馈信号共同构成决策输入；LLM 负责生成易懂说明，规则引擎始终握有推荐边界。

完整投顾流程架构

理财顾问 / 客户 推荐、比较、配置需求
→
Router Agent 识别投顾意图、校验角色
→
客户身份校验 customer_id、状态、会话归属
→
风险画像与动态约束 风评、持仓、预警、适当性
→
AdvisorAgent 七工具 LLM 选择并编排工具
→
产品推荐与资产配置 匹配度、比例、预算分配
→
业务操作 Agent 确认后进入受控交易链路
→
Outbox / Redis Pub/Sub 推荐、成交与偏好事件联动
→
Memory Manager 会话、画像、事实、图谱回写

答辩时我会强调：投顾建议不是孤立对话，而是由身份、事实、规则和事件共同约束的一条金融服务链。advisor_agent.py 负责工具编排；真正的交易确认、适当性校验和状态落库仍在后续受控业务链路完成。

答辩亮点：先风评、后精推的双重保护

① 推荐请求AdvisorAgent 的 smart_recommend 先读取客户画像，并校验最近一份风评的有效期。
② 画像缺失 / 风评过期前端根据 /risk/assessment-status 提示 风险测评提醒弹窗，客户可直接进入 16 题风险测评；投顾链路同步返回清晰的测评提示。
③ 测评完成生成 C1–C5 风险等级，恢复“画像 + 持仓 + 偏好 + 产品适当性”的全量个性化推荐与资产配置。
④ 未完成时的后端兜底系统不让推荐中断，但强制按 C1 保守型匹配，仅输出 R1 低风险产品，同时保留“完成风评后可获得更精准建议”的引导。

这不是单纯的 UI 提示：前端弹窗改善体验，后端 C1 / R1 降级保护保证即使绕过页面也不会得到超适当性的推荐。代码依据：AppLayout.vue、app/api/risk.py、advisor_agent.py。

七工具：让模型编排，让服务给出事实

01

smart_recommend

组合入口：串联画像、预警、候选产品与配置建议，确保一次推荐使用同一份约束条件。

02

profile_tool

读取客户风险等级、画像维度与诊断规则，为“适合谁”提供事实基础。

03

recommend_products

在适当性与动态风险约束后的候选池中计算匹配度并排序。

04

asset_allocation

将客户可承受风险转成可解释的资产比例建议，并支持预算分配。

05

analysis_holdings

读取 MySQL 持仓与 Neo4j 关系，识别集中度、缺口与已有暴露。

06

compare_customers

用于顾问侧同类客群对比，帮助解释客户分层与推荐差异。

07

graphrag_search

结合 Milvus 语义召回与 Neo4j 关系上下文，补充产品知识和推荐理由。

技术栈

LLM 不是单独决策者

  • LangChain：将 LLM 与工具箱组合
  • Profile/Holding/Recommendation/Allocation Tool：给出事实和计算
  • Redis：会话与跨会话记忆召回
  • MySQL、Neo4j、Milvus：业务事实、关系和知识上下文
合规约束

把“能说”与“能推荐”分离

  • 产品风险不能超过客户适当性范围
  • 风险预警会收紧推荐范围与文案
  • 配置输出保留风险提示和推荐依据
  • 拒绝反馈影响后续偏好信号，不自动调级

设计亮点

多工具协同

把画像、持仓、候选池、配置模板拆成原子能力，便于替换与审计。

可解释链路

GraphRAG 将产品知识与关系上下文注入解释，避免只给黑盒匹配分。

实时体验

流式执行让顾问在复杂工具链路完成时仍可持续看到答复进度。

需求文档与当前实现：从功能清单到可运行的投顾链路

需求映射：需求文档要求投顾助手完成“客户画像分析、产品推荐、资产配置建议、持仓穿透”，并以 GraphRAG 形成比纯 RAG 更完整的推荐依据。当前实现以画像、持仓、推荐、配置和知识工具组成可追踪工具链，而非让模型直接给出不可验证结论。

需求文档中的基础能力

  • 客户画像分析与风险偏好识别
  • 产品推荐、资产配置与持仓穿透
  • GraphRAG 连接产品知识与关系信息
  • 面向客户和顾问的智能投顾交互

当前工程增强

  • LLM 在七工具之间自主编排，smart_recommend 封装高频组合链路
  • 风评缺失/过期触发弹窗与 C1/R1 保守降级，前后端双重保护
  • 按金额生成预算分配，并以角色化叙事区分顾问报告与客户表达
  • SSE 工具进度展示调用阶段，风险事件可收紧候选池并进入事件闭环

推荐结果如何进入金融级闭环

投顾建议产品、比例、预算分配、理由
→
客户确认建议与正式指令分离
→
业务操作 Agent权限、适当性、二次确认
→
交易 / 推荐事实MySQL 业务数据
→
Outbox与业务事务一起落库
→
Redis Pub/Sub画像、风控、图谱订阅
→
Memory Manager下一次服务读取最新状态

这条链路说明“推荐”如何成为可追溯的服务事实：若客户确认购买，业务操作 Agent 才会执行交易；成交、拒绝或风险预警都通过 Outbox 和 Redis Pub/Sub 驱动后续画像、风控与关系图谱更新。

从“经验推荐”到“证据推荐”

顾问不再逐页翻产品手册：Agent 同时读取客户风险等级、持仓行业分布、产品适当性与知识上下文。输出不仅有“推荐什么”，还保留“为什么适配、受什么约束、风险在哪里”。

可回答的技术追问

  • GraphRAG：Milvus 语义召回 + Neo4j 关系补全
  • 适当性：C1-C5 与产品风险范围作为确定性过滤
  • 体验：SSE 流式响应，工具调用结果可结构化展示
  • 治理：风险事件能实时收紧候选池，而非事后提示

亮点：预算分配与角色化表达

当顾问给出投资金额时，系统可将配置比例转化为具体预算分配；顾问端保留画像、约束和产品匹配等专业信息，客户侧则用更易理解的叙事输出建议与风险提示。

边界：投顾不越权

AdvisorAgent 不直接执行交易，也不修改正式风险评级。它输出的是被画像、适当性和预警约束的可解释建议；交易与评级分别继续走业务操作和正式风评/审计流程。

投顾 Agent 解决的核心痛点

动态多表联查 + Cache-Aside

画像不再依赖静态标签，而是基于客户、测评、持仓、产品和交易事实动态计算。查询优先读取 Redis，未命中再访问 MySQL 并回填缓存；MySQL 始终是可审计的业务事实来源。

七大核心工具

smart_recommend、画像、产品、配置、持仓、客群对比与 GraphRAG 工具共同覆盖推荐闭环。LangChain 仅负责工具编排，确定性规则和业务服务仍保持独立可控。

Neo4j 同步失败

图谱是 MySQL 业务事实的可重建投影。同步异常进入可观测重试与人工介入队列，不以图谱失败覆盖或篡改主数据。

默认 R1 推荐

客户未完成或风评已过期时，链路先提示完成测评，并仅开放保守候选池；这是一项临时推荐约束，不会自动变更正式风险等级。

受控复核与保守策略

行为信号出现显著偏离时，系统收紧候选范围、强化风险提示并触发受控复核，完整保留证据与审计记录。

从“经验推荐”到“证据推荐”

治理边界

AdvisorAgent 不直接执行交易，也不修改正式风险评级；正式 C1-C5 的变化只由正式风险测评与审计流程完成。

需求映射

客户画像、持仓分析、产品匹配、资产配置和 GraphRAG 组成从事实依据到客户解释的可追溯链路，让每一条推荐都有来源、约束和理由。
