终章结论

多 Agent 的关键不在“数量”，而在事实一致、事件可追溯、消费可幂等

统一入口隐藏复杂性，Router 与 ChatOrchestrator 提供横切管控；跨 Agent 协作以业务事实为起点，通过 Outbox 和 Redis 广播形成可恢复的领域事件链路。

全平台分层流程

Vue 3 前端 客户对话、顾问、风控、运营
→
FastAPI / API HTTP / SSE、认证与响应契约
→
Router + Orchestrator 意图分发、风险预检、追踪
→
六类 Agent 客服、画像、投顾、风控、操作、分析
→
服务 / 工具 / 规则 LLM、RAG、推荐、交易、规则引擎
→
五类底座 MySQL、Redis、Neo4j、Milvus、MinIO

连接语义：HTTP/SSE 承载交互，SQLAlchemy Async 管理事实数据，Redis Pub/Sub 承载领域事件，Neo4j/Milvus 支持关系与语义检索。

闭环一：交易风险如何影响全链路

业务操作 交易请求与事前评估
→
风险预警 预警事实写入 MySQL
→
Outbox 事务提交后可靠投递
→
Redis 广播 `event:agent_domain`
→
画像 / 投顾 / 客服 动态标记、推荐约束、风险提示

合规约束 消费使用 `event_id + consumer` 幂等记录；风险事件改变的是动态策略状态，不自动修改正式 C1-C5 风险等级。

闭环二：推荐反馈与数据洞察

投顾推荐 客户拒绝原因
→
反馈事件 偏好信号
→
客户画像 更新避免类别
→
下一次推荐 候选池排除
NL2SQL 只读结果
→
洞察提取 客户、时间、数值、证据齐全
→
领域事件 受控发布
→
投顾 / 风控 / 画像 消费策略信号

统一事件信封

事件含 `event_id`、`event_type`、`source_agent`、客户、关联 ID、时间与不可变 payload，让业务事实可定位、可重放。

事实优先

MySQL 中的交易、预警与处理状态是事实源；缓存和广播用于加速与协作，不能替代事实判断。

可扩展而不失控

新增 Agent 只需声明生产/消费的领域事件与契约，不应绕过统一入口或自行修改核心风险等级。
