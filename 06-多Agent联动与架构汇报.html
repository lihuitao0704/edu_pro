终章结论

多 Agent 的关键不在“数量”，而在事实一致、事件可追溯、消费可幂等

统一入口隐藏复杂性，Router 与 ChatOrchestrator 提供横切管控；跨 Agent 协作以业务事实为起点，通过 Outbox 和 Redis 广播形成可恢复的领域事件链路。

全平台分层流程

Vue 3 前端 客户对话、顾问、风控、运营
→
FastAPI / API HTTP / SSE、认证与响应契约
→
Router + Orchestrator 意图分发、风险预检、追踪
→
六类 Agent 客服、画像、投顾、风控、操作、分析
→
服务 / 工具 / 规则 LLM、RAG、推荐、交易、规则引擎
→
五类底座 MySQL、Redis、Neo4j、Milvus、MinIO

连接语义：HTTP/SSE 承载交互，SQLAlchemy Async 管理事实数据，Redis Pub/Sub 承载领域事件，Neo4j/Milvus 支持关系与语义检索。

闭环一：交易风险如何影响全链路

业务操作 交易请求与事前评估
→
风险预警 预警事实写入 MySQL
→
Outbox 事务提交后可靠投递
→
Redis 广播 `event:agent_domain`
→
画像 / 投顾 / 客服 动态标记、推荐约束、风险提示

合规约束 消费使用 `event_id + consumer` 幂等记录；风险事件改变的是动态策略状态，不自动修改正式 C1-C5 风险等级。

闭环二：推荐反馈与数据洞察

投顾推荐 客户拒绝原因
→
反馈事件 偏好信号
→
客户画像 更新避免类别
→
下一次推荐 候选池排除
NL2SQL 只读结果
→
洞察提取 客户、时间、数值、证据齐全
→
领域事件 受控发布
→
投顾 / 风控 / 画像 消费策略信号

统一事件信封

事件含 `event_id`、`event_type`、`source_agent`、客户、关联 ID、时间与不可变 payload，让业务事实可定位、可重放。

事实优先

MySQL 中的交易、预警与处理状态是事实源；缓存和广播用于加速与协作，不能替代事实判断。

可扩展而不失控

新增 Agent 只需声明生产/消费的领域事件与契约，不应绕过统一入口或自行修改核心风险等级。

场景1：用户发起交易

用户购买基金；客服理解需求，业务操作创建申请，风控审核，画像消费成交事实。

用户/客服交易诉求
→
业务操作申请与确认
→
风控适当性审核
→
Event Bustransaction.completed
→
画像/Memory偏好、交易、图谱

事件：交易金额、产品、状态。Memory：Redis 回执；MySQL 流水/画像；Milvus 服务摘要；Neo4j 客户—产品关系。

场景2：大额转账风险审核

“我要转账50万元”；业务操作与安全 Agent 共同核验，风控检查金额、历史行为、账户风险与 AML。

用户大额转账
→
业务/安全参数、身份、设备
→
风控AML 与行为检查
→
Event Busrisk.transfer.assessed
→
执行/复核/拦截状态更新

Memory：Redis 待复核；MySQL 审核轨迹；Milvus 核验摘要；Neo4j 资金与风险关系。

场景3：风控发现风险，驱动投顾调整策略

持仓集中度过高、账户回撤严重；风控事实广播后，投顾收紧候选池并重算配置。

风控集中度/回撤预警

Event Busrisk.alert.created
→
投顾降低高波动上限
→

合规边界：更新动态约束，不自动修改正式 C1-C5 等级。

场景4：投顾推荐产品，风控审核

投顾推荐高收益理财；风控与合规分别检查风险等级、适当性、资产比例与披露。

Memory：推荐版本、审核证据、展示偏好与产品—适当性关系。

用户确认投顾建议；交易 Agent 以审批通过的推荐为输入，执行前再做关键约束复核。
